## 1. Why `bronze_cnpj_estab_quarantine` needed migrating at all

Before this migration, `bronze_cnpj_estab_staging` carried 35 columns and
`bronze_cnpj_estab_quarantine` carried 36 — neither carrying
`_snapshot_month` or `_snapshot_ref_date`. That gap is not new: F1.4a
(2026-07-31) added the two columns to `bronze_cnpj_estabelecimentos` alone, so
staging and quarantine were left behind — the module docstring's own
"THREE TABLES AND NOT ONE" block records the measured 35/36-column gap
(`scripts/backfill_snapshot_columns.py:11-21`).

Quarantine's 36 columns are not an accident of this phase — they are F1.3's DQ
gate doing exactly what it was built to do. `databricks/src/dq_gate_batch.py:85`
appends the gate's reject frame with
`bad.write.format("delta").mode("append").saveAsTable(quarantine)`, with no
`mergeSchema`; when the target table does not yet exist, `saveAsTable` creates
it from whatever frame is appended — including an empty one. Quarantine's
complete Delta history has exactly that event as version 0
(`CREATE TABLE AS SELECT`; independently re-confirmed in
[§10](#10-cleanup-reverted-and-redeployed--confirmed-in-the-deployed-state)).
An empty reject frame, at zero rejects, still created the table — which is how
quarantine ended up with 36 columns (staging's 35 plus `_dq_reject_reason`)
with nobody having decided to add a 36th column; it fell out of the gate's own
append path.

Nobody had noticed because nothing had yet forced the mismatch open. This repo
does not write with `mergeSchema` anywhere, deliberately — a schema is a
contract, and a write that widens it unasked is drift discovered later rather
than now. So the mismatch stays invisible until the next estab ingest actually
sends a 37-column stream against 35-column staging, and the gate then tries to
append a 38-column reject frame into 36-column quarantine.

Both directions of that append were probed before Task 1 was dispatched,
specifically to avoid asserting Delta's append semantics from memory. The
probe was a throwaway script, run with `uv run python` against the repo's own
local Delta session factory, `opl.spark.local_session` — `local[2]`,
`spark.driver.memory 2g`, Delta 3.3.1, the same session configuration
`tests/` uses — and lived only in the session scratchpad, not in the repo.
Its two cases mirror the exact shapes at issue: case A a target with **fewer**
columns than the incoming frame (the quarantine hazard: a 36-column table
receiving a wider reject frame), case B a target with **more** columns than
the incoming frame (the repromote hazard: a wider staging/bronze table
receiving a narrower one). Case A's target was emptied with `DELETE FROM`
before the append, deliberately, to mirror `bronze_cnpj_estab_quarantine`
holding 0 rows. Verbatim output, both cases:

```
A: target probe_db.narrow_target has 3 cols and 0 rows
A: RESULT = APPEND FAILED -> AnalysisException: [_LEGACY_ERROR_TEMP_DELTA_0007] A schema mismatch detected when writing to the Delta table (Table ID: aca97315-f5c3-4d8a-a589-5e4193ec99d4).
B: target probe_db.wide_target has 5 cols
B: RESULT = APPEND SUCCEEDED
B:   {'a': 'a1', 'b': 'b1', 'c': 'c1', '_snapshot_month': '_snapshot_month1', '_snapshot_ref_date': '_snapshot_ref_date1'}
B:   {'a': 'a1', 'b': 'b1', 'c': 'c1', '_snapshot_month': None, '_snapshot_ref_date': None}
```

Case A's target is reported as `3 cols and 0 rows` on the same line as the
verdict, which is what makes "it fails even when the target holds 0 rows" a
measured fact rather than an inference — the row count and the failure sit in
the same transcript. `refuse_non_empty_quarantine`'s own docstring
(`scripts/backfill_snapshot_columns.py:271-277`) cites the same error for this
direction: "probed, and it fails against a 0-row target too
(`_LEGACY_ERROR_TEMP_DELTA_0007`)" — an append carrying more columns than its
Delta target raises `AnalysisException`, even against an empty table.

Case B's two result rows show the NULL fill directly, not merely a successful
append: the first row was written with all five columns populated; the
second was appended by a three-column frame and comes back with
`_snapshot_month: None, _snapshot_ref_date: None`. So a target with **more**
columns than its incoming frame does not raise under Delta's schema
enforcement — it appends, and the columns the frame lacks land NULL for those
rows. That is the shape of the repromote hazard this migration also closes:
before quarantine carried the two snapshot columns, a batch corrected and
re-appended through `repromote_triaged_batch` into a wider staging/bronze
table would have gone in two columns short and landed NULL quietly rather
than failing loud.

A separate probe, run during Task 1 itself and quoted in the implementer's own
report, answers a different question: not whether columns are missing or
extra, but whether a same-column-set append arriving in a **different order**
resolves positionally or by name. That question exists because after this
migration staging ends `[..., _snapshot_month, _snapshot_ref_date]` while
quarantine ends `[..., _dq_reject_reason, _snapshot_month,
_snapshot_ref_date]` — the same column set, different order — and the gate's
future reject frame is ordered like quarantine's, not staging's. Probed
locally against Delta (a target created by SQL DDL in one column order,
appended with a same-named frame in a different order via
`mode("append").saveAsTable`):

```
PROBE _snapshot_month   = '2026-07'
PROBE _dq_reject_reason = 'bad_cnpj_basico_length'
PROBE VERDICT: BY NAME
```

`saveAsTable` resolves **by name** (`AppendData.byName`), not by position, so
the order difference is not a hazard — a separate result from, and not a
restatement of, the missing/extra-column probe above.

So the migration closes both directions at once — the 37-into-35 failure that
would stop the next ingest outright, and the 38-into-36 (and narrower-frame)
failures that would stay latent until a dirty row or a repromote actually
exercised them. The module docstring calls the second "the worse one: it needs
a dirty row to appear, so it can stay latent for months after the expensive
ingest that unblocked it" (`scripts/backfill_snapshot_columns.py:19-21`).

**Pre-migration state, measured before any of this ran:** staging held 35
columns with neither snapshot column; quarantine held 36 columns with neither;
the column-set diff at that point showed `quarantine == staging +
_dq_reject_reason` exactly — the arithmetic this section depends on, confirmed
independently in
[§10](#10-cleanup-reverted-and-redeployed--confirmed-in-the-deployed-state).

## 3. Two defects this task found outside its own listed scope

Both would have surfaced later, and more expensively, than they did here.

### 3.1 Constraint DDL was being applied to whichever table the script wrote, not only to bronze

Before `0678e7d`, `_assert_constraints` applied `spec.constraints` — bronze
DDL: `ALTER COLUMN cnpj_basico SET NOT NULL` and
`CHECK (length(trim(cnpj_basico)) = 8)` — to whatever table `main` had just
written, unconditionally. Once a third argument let that target be staging or
quarantine, an original `--staging` run would have finished `DONE`, printed
`re-asserted 3 constraint statement(s)`, and left the constraint sitting on
staging.

That is a landmine, not a no-op: `opl.bronze.rules` declares
`null_or_empty_cnpj_basico` and `bad_cnpj_basico_length` because rows like that
arrive — into staging, which is exactly where the DQ gate expects to catch and
reject them. A `NOT NULL`/`CHECK` planted on staging would instead fail the
next ingest's Delta write for precisely the row the gate exists to route into
quarantine. The RED-phase test reproduced the pre-fix code issuing those three
statements without error against today's estab data:

```
def test_no_constraint_ddl_is_issued_against_staging_or_quarantine(tbl, capsys):
    ...
>       assert spark.statements == []
E       AssertionError: assert ['ALTER TABLE...asico)) = 8)'] == []
---------------------------- Captured stdout call -----------------------------
backfill: re-asserted 3 constraint statement(s) on workspace.default.bronze_cnpj_estab_staging
```

Today's estab data satisfies both statements, so a `--staging` run under the
original plan would have gone green and the damage would only surface whichever
month first produced a dirty `cnpj_basico` — the same "latent is worse than
loud" shape as the append hazard in [§1](#1-why-bronze_cnpj_estab_quarantine-needed-migrating-at-all).

Fixed in `0678e7d` by scoping the DDL to fire only when the resolved table
equals `DEFAULT.table(spec.bronze)`; on staging or quarantine the script
instead prints why the statements were **not** issued (quoted live in
[§6](#6-the-quarantine-run) and [§7](#7-the-staging-run--71874448-rows)).

### 3.2 The DONE line claimed a new Delta version unconditionally, even on a run that committed nothing

`1d72a1b`'s own fix — skip the write when there are no rows to fill — broke the
final `DONE` line as an unintended consequence, found and fixed in the same
round. On a **repeat** over an already-migrated 0-row target, `missing_columns`
is also empty, so there is no `ALTER` either and the run commits nothing at
all. The unfixed line would have named the pre-run baseline `version` as "the
way back" — a version nothing this run superseded.

That is exactly the shape of F1.4a's real incident: a Databricks
`INTERNAL_ERROR` retried the backfill task past `max_retries: 0` and produced a
second attempt whose own printed "the way back" version was likewise
post-baseline rather than the true rollback target — `docs/f1.4a-migration-evidence.md`,
§7.2 ("The failure triggered a retry past `max_retries: 0`"). That document
records the operator-facing cost of exactly this shape — a printed version
number that is not the way back, read right at the moment it matters most.

Fixed with a conditional keyed on `wrote or to_add` (later extracted into
`_done_line` in `c757d94`); the happy-path string stayed byte-identical to what
`docs/f1.4a-migration-evidence.md` quotes.

Raised by CodeRabbit on PR #7, which read Databricks' published reference —
"The position (numbered from `1`) of the column within the relation" — and asked

measurement is what this workspace does. Run against warehouse `13cf10c85b0f189d`:

```
0       | 36      | 37
```

A 37-column table numbered 0 through 36 is 0-based, unambiguously — 1-based
numbering of 37 columns would give `min_ord = 1, max_ord = 37`. The listing above

so both are written down and the disagreement is left visible. What the next
reader needs is that the two do not agree, and the query that settles it for
their own workspace.

draws from an ordinal is §24.3's: `_batch_id` returns `ordinal_position = 34` on

statistics for by default, so the finding — that `_batch_id` was outside the

## 9. UC planned the staging overwrite as a table REPLACE, not `OverwriteByExpression`

```sql
SELECT version, operation FROM (DESCRIBE HISTORY workspace.default.bronze_cnpj_estab_staging) ORDER BY version
```
```
version | operation
--------+-----------------------------------
0       | CREATE TABLE
1       | STREAMING UPDATE
2       | STREAMING UPDATE
3       | SET TBLPROPERTIES
4       | COMPUTE STATS
5       | ADD COLUMNS
6       | CREATE OR REPLACE TABLE AS SELECT
(7 row(s))
```

Version 6 is `CREATE OR REPLACE TABLE AS SELECT`, with
`"isV1SaveAsTableOverwrite":"true"` in its `operationParameters`.
`_assert_constraints`' own docstring documents this branch as unknowable from
the client — which of `OverwriteByExpression` (keeps metadata) or
`AtomicReplaceTableAsSelect` (drops CHECK constraints and NOT NULL) Unity
Catalog picks for `mode("overwrite").saveAsTable` "is not observable from here
without running it against the workspace." This run is what ran it against the
workspace, against a real 71.9M-row managed UC table: **UC picked the
replace.**

Table properties survived it:

```sql
SHOW TBLPROPERTIES workspace.default.bronze_cnpj_estab_staging
```
```
delta.enableDeletionVectors                    | true
delta.enableRowTracking                        | true
delta.parquet.compression.codec                | zstd
delta.workloadBasedColumns.deltaFileStatistics | `_batch_id`
... (15 row(s))
```

`delta.workloadBasedColumns.deltaFileStatistics` was set in version 3
(`SET TBLPROPERTIES`) and survived version 6's replace intact. Staging carries
no CHECK constraint and no column mask, so nothing was lost here, and
`_assert_constraints`'s skip on staging ([§3.1](#31-constraint-ddl-was-being-applied-to-whichever-table-the-script-wrote-not-only-to-bronze))
cost nothing.

**The consequence, stated plainly:** a CHECK constraint, a NOT NULL, and a UC
column mask are not table properties, and are not carried through a replace the
way the property above was. Quarantine's complete history is two versions —
v0 `CREATE TABLE AS SELECT`, v1 `ADD COLUMNS` — with no third, write-shaped
commit ([§6](#6-the-quarantine-run)). So on the one target where
`fill_and_overwrite` ([§3.2](#32-the-done-line-claimed-a-new-delta-version-unconditionally-even-on-a-run-that-committed-nothing))
skips the write entirely, no replace happened: **the 0-row skip prevented a
real table replace, not a hypothetical one.** Had the pre-fix behavior in
either §3.1 or §3.2 reached a masked or constrained non-bronze target, this is
the mechanism that would have executed against it.

This is now a measured, durable fact about how this repository's overwrites
behave against a managed UC table — not only about this migration. Whether it
deserves its own ADR, and whether it graduates beyond this run-evidence doc, is
an open question left for Task 7 to decide; it is recorded here rather than
left to be re-derived.

It can also be a stale wheel inside a fresh deploy -- the jobs receive the wheel through the glob `dependencies: ["../../dist/*.whl"]` over a dist/ that nothing cleans.
```
Deploy, then launch again with the same revision.
```

### 12.3 The retry that should not have happened

`assert_deployed_revision` declares `max_retries: 0`, and the platform ran it
twice anyway against the same run — `attempt 0` then `attempt 1`, both
`FAILED`. The cause: an uncaught exception leaves the task's lifecycle state
`INTERNAL_ERROR`, and `max_retries` governs clean task failures, not
`INTERNAL_ERROR` — a fact this repo already carries, in
`docs/adr/0008-pii-masking-socios.md:143` and in
`docs/f1.4a-migration-evidence.md`, §7.2 ("the failure triggered a retry past
`max_retries: 0`"), but never before observed on a task whose entire job is to
refuse.

It is harmless here, and the reason is structural rather than lucky: the guard
reads two strings and writes nothing, so it is idempotent by construction and
refused identically on both attempts. The durable consequence is not scoped to
this one guard: **any task placed first in a job as a guard must be
side-effect-free**, because `max_retries: 0` will not protect a task that
writes something and then gets retried by the platform against its own
declared setting.

### 12.4 Filename caching — ruled out by measurement

`pyproject.toml` declares a static `version = "0.0.0"`, so the wheel filename
(`open_payments_lakehouse-0.0.0-py3-none-any.whl`) never changes across
rebuilds. The concern: if serverless caches an install by filename, a redeploy
could leave the **old** stamped wheel installed under an unchanged name, and
every guarded job would refuse permanently — a state indistinguishable from a
broken guard.

The discriminator is `opl_smoke`, which reads `built_revision()` from the same
wheel, the same `environment_key` and the same
`dependencies: ["../../dist/*.whl"]` glob as every guarded task, and cannot
refuse because it carries no guard. Two runs bracket the second deploy: run
`136918510113031` reported
`built_revision='2396af361702f645f51dab5d201f1c8271cf0952'` before it, and run
`796168381085213` reported
`built_revision='109ac6eee6550d4fd7c2f74d4c72a089177de38b'` after it — the same
wheel filename, different content read back both times. No caching, so no
`dist/` emptying and no version bump were needed. This is a second reason
`opl_smoke` stays deliberately unguarded rather than merely exempt: it is the
one job that can answer "what is actually installed" without itself being
subject to the question it would need to answer.

### 12.5 A distinction claimed, then retracted

The controller's dispatch for this step asked for confirmation that the
wrong-revision refusal message is distinguishable from a stale-deploy message.
It is not, and cannot be: `_refuse_the_mismatch` branches on what the deployed
value **is** — a well-formed object name that fails to match — and a
genuinely stale deploy and an operator's mistyped `--params revision=`
produce exactly that shape. From inside the run both are the same fact,
expected != actual, and nothing reachable from a job can see the operator's
repository to tell them apart. The message is written accordingly, as a hint
rather than a determination — "The likeliest cause is the simplest" — naming
both revisions and stating a likeliest cause without asserting it.

The implementer's own report had implied, in its Step 6 planning notes, that
the message could make this distinction; the report retracts that in the same
section the live refusal is quoted in, rather than treating it as a limitation
discovered late. It is the second controller-authored specification defect
found this phase — the first was the verification gate specified against a
state that could not exist yet, already recorded in
[Gate item 3](#gate-item-3--specified-against-a-state-that-could-not-exist-yet).
In both cases the implementer reported the mis-specification instead of
manufacturing a result that would have satisfied it as written.

### 13.6 Rates — the multipart advantage, and why single-PUT is not a bandwidth number

| subset | objects | bytes | wall clock | MB/min | PR A |
|---|---|---|---|---|---|
| multipart | 20 **of 21** | 6,530,134,947 | 2,376.7 s | **164.9** | 94.7 |
| single PUT | 9 | 444,440,799 | 1,077.1 s | **24.8** | 24.8 |

> **The multipart row excludes one object, and this is the disclosure it was
> missing** (added 2026-08-03, final review). [§13.4](#134-verification-all-30-objects-byte-for-byte)
> lists **21** multipart objects totalling 6,899,105,510 B; the row above covers
> 20 of them, and the one left out is **`Estabelecimentos9.zip` (368,970,563 B)** —
> the last object of the last group of the run. **Why it is out is not recorded in
> the captured log**, and rather than guess at a reason this states the gap and
> bounds it. The bound is arithmetic: the whole run took 3,584.7 s, of which
> 2,376.7 + 1,077.1 = 3,453.8 s is accounted for above, leaving a **130.9 s
> residual** — consistent with the missing object having taken about that long,
> which would put it at ~169 MB/min, in family with the other twenty. Folding it
> in moves the multipart rate from 164.9 to **165.1 MB/min** and the advantage
> ratio from 6.65× to 6.66×. **No conclusion below changes**, which is why the
> measured 20-object figure is kept as the headline rather than replaced by a
> reconstructed 21-object one. [§26.3](#263-adr-corrections-0005-0007-and-0008)
> identifies the same object from the byte difference.

**Single-PUT reproduced PR A exactly: 24.8 MB/min**, on a different day, on
near-identical bytes (444,440,799 B here in 1,077.1 s; 444,421,834 B in PR A
in 1,076 s), flat at 23.8-25.1 MB/min per object across all nine.
**Multipart ran 1.74× faster than PR A observed** — 164.9 MB/min against
94.7, peaking at 199.3 MB/min on `Estabelecimentos0.zip` and 197.8 on
`Empresas0.zip`; the largest objects were the fastest.

**So the multipart advantage over single PUT was 6.6× this run, not the
3.8× ADR 0007's figures imply** (164.9 / 24.8 = 6.65). And since the same
link, session and client moved multipart bytes at up to 199.3 MB/min while
single PUT held at 24.8 both here and in PR A, **single PUT's 24.8 MB/min is
not a bandwidth limit — it is a stable per-request property**, observed to
three significant figures across two runs on different data. That is a
stronger statement than either measurement alone supports, and it changes
what ADR 0007's 94.7/24.8/3.8× figures mean: they describe PR A's sample,
not this link's throughput generally. This corrects ADR 0007's Consequences
section, whose bullet reads the 3.8× figure as though it generalises.

## 14. Task 5 Step 0 — the Auto Loader state is now month-scoped

**No run in this section. This is a code change made *before* the 2026-07
ingests, and the operational consequence it creates is the reason it is in this
document rather than only in a task report.**

### 14.1 What was wrong, and what changed

`src/opl/bronze/autoloader.py` keyed both `schema_location` and
`checkpoint_location` on `table_key` alone, while the stream's source path is
month-scoped (`DEFAULT.landing_table(spec.subdir, month)`). Every ingest through
2026-06 ran under that layout, so it was never exercised: PR A's empresas and
socios streams were first runs. The first 2026-07 ingest would therefore have
restarted a live streaming query against a **different source directory** — which
Spark's "Recovery Semantics after Changes in a Streaming Query" lists as
"generally not allowed as the results are unpredictable", defining *not allowed*
as "the restarted query is likely to fail with unpredictable errors". Databricks
states the positive rule for Auto Loader directly: more than one source data
location loaded into one target table "requires a separate streaming checkpoint".

The locations are now `_checkpoints/<month>/<table_key>` and
`_schemas/<month>/<table_key>` — **siblings of**, never children of, the existing
`_checkpoints/<table_key>` directories, so nothing new is written inside a
checkpoint directory a 2026-06 query still owns.

Two things this is deliberately **not**:

- It is **not** the silent-success case `registry.py`'s checkpoint-namespace guard
  warns about. Auto Loader's exactly-once tracking is keyed on the full file path,
  and 2026-07's paths are all new, so a query that starts ingests them correctly.
  The risk was failure at startup, not an under-ingest reported as SUCCESS.
- It is **not** resting on `spark.databricks.cloudFiles.checkSourceChanged`. That
  guard is active and its trip is a loud `[STREAM_FAILED]`
  `StreamingQueryException`, but the documented example is a cross-*bucket*
  mismatch under file-notification mode. Whether it fires for a same-Volume,
  different-subdirectory change under the directory-listing default this job uses
  is **not stated by the docs and has not been measured here**. The layout was
  fixed instead of the guard relied on.

`Trigger.AvailableNow` changes none of the above.

### 14.2 ⚠️ 2026-06 must not be re-run through the ingestion flow

The 2026-06 state at the old, unscoped paths is now **orphaned**: nothing reads
it, and it is left exactly where it is, because streaming state is never
migrated. The cost of that decision is the one thing an operator has to carry
forward:

> A 2026-06 ingest launched through the job flow now finds an **empty**
> month-scoped checkpoint, treats every 2026-06 file as new, and appends that
> month's rows into staging a second time under a fresh `_batch_id`. The
> promote's idempotence is keyed on `_batch_id`, so it **cannot see the
> duplication** and will carry it into bronze. Nothing fails. The row counts
> double.

What does and does not protect against this:

- **Not** `max_retries: 0`, and not the platform. A retry past `max_retries: 0`
  on `INTERNAL_ERROR` is already observed twice in this repo
  ([§12.3](#123-the-retry-that-should-not-have-happened),
  `docs/f1.4a-migration-evidence.md` §7.2).
- **Partly** the `revision` job parameter. Every ingestion job defaults `month`
  to `2026-06`, so a bare `databricks bundle run bronze_cnpj_<table> -t free`
  would target exactly the month at issue — but `revision` defaults to
  `REQUIRED-PASS-A-REVISION`, which `assert_deployed_revision` refuses first
  (ADR 0009). So the accident needs a deliberate `--params month=2026-06` with a
  valid revision; it is not one keystroke away.
- **Nothing else.** There is no code guard that refuses an already-ingested
  month. Re-running a month that has already been promoted is a manual,
  deliberate act, and it requires deciding what to do about the duplicate batch
  before launching, not after.

The same statement lives on `checkpoint_location`'s own docstring, which is where
a reader who wonders why an unread `_checkpoints/bronze_cnpj_lookup` still exists
in the Volume will arrive.

### 14.3 What Steps 1–6 should watch for

- **Every 2026-07 ingest is a FIRST run against an empty checkpoint**, by
  construction. The first `ingest` task's duration is therefore a cold-start
  number with no prior offsets to skip, and there is nothing to compare it
  against from 2026-06.
- **Nothing should appear under a 2026-06 state path during Step 2.** After the
  empresas run, `_checkpoints/` should hold the pre-Step-0 `<table_key>`
  directories untouched plus a new `2026-07/` directory, and no `2026-06/`
  directory at all. A `2026-06/` appearing there means a month reached the
  checkpoint that did not reach the source path.
- **Empresas first is now load-bearing, not incidental.** It is the smallest of
  the three, so this layout decision is validated before ~25 GB of
  estabelecimentos is read under it. Keep that order for that reason.

### 16.1 The mechanism is wiring, not `retention.py`

1. `reclaim_landing` is `depends_on: promote`; `promote` is `depends_on:
   [check_bad_rows, outcome: "true"]`. **Any batch with at least one reject
   never reaches reclaim.**
2. The batch that *does* hold the rows is then promoted by
   `repromote_triaged_batch`, whose task graph is only
   `assert_deployed_revision` and `promote` — **no reclaim task**, confirmed
   in the job YAML.
3. A later clean run cannot compensate: its own batch ingests nothing,
   because the checkpoint has already consumed the files, so its own reclaim
   correctly refuses too.

`retention.py` behaved correctly at every step it was reached, and its own
printed message even names case (a) and supplies the confirming query. The
control is not broken; it is **unreachable**.

[§13.8](#138-for-task-5--the-48-gb-peak) projected — ~48 GB, 2.18× this
Volume's demonstrated high — is not a one-off squeeze against a single
month's upload; it is **the floor for every month F1.4b or a later phase
adds**, against a Volume with no published quota.

### 20.2 The four rejects, and the triage-doctrine correction

```
_dq_reject_reason         | rows | rescued_null | rescued_NOT_null
encoding_replacement_char |    4 |            4 |                0
```

**This is the document's most consequential finding.** The controller's own
dispatch instruction for triage read: for each rejected row, is
`_rescued_data` null? If it is not, the parse is wrong and that is a defect,
not source dirt. All four of these rejects have `_rescued_data` **NULL** — and
are, nonetheless, a parse defect. Following the instruction as written would
have repromoted four rows with lost bytes into bronze.

The reason is what the reject reason names. `_rescued_data` NULL says the CSV
**field-splitting** consumed every field and left nothing over; it says
nothing about **character decoding**, which happens independently — so for
this one rule the standing test is necessary but not sufficient.
`CSV_DIALECT["encoding"]` is `cp1252`. windows-1252 leaves five byte values
undefined (`0x81 0x8D 0x8F 0x90 0x9D`); Java's decoder substitutes U+FFFD for
them **silently**, where Python raises. A U+FFFD here means a source byte was
**lost**, not that a wrong codepage was applied. Nothing is *rescued*, because
the parse succeeded — lossily.

Which column carries it was, in
[ADR 0006](adr/0006-bronze-dq-gate-policy.md)'s own words, "not yet known". It
is now:

```
cnpj_basico | email_with_marker | len | pos
02546225    | [{FFFD}]          |   1 |   1
02586244    | [{FFFD}]          |   1 |   1
02631716    | [{FFFD}]          |   1 |   1
02653802    | [{FFFD}{FFFD}]    |   2 |   1
```

**`correio_eletronico`, in all four — and the field's entire content is the
undecodable byte(s).** There is no truncated address and no real email being
lost: the source field held one or two bytes that are not cp1252 and nothing
else. Every other column of all four rows parsed cleanly. Verdict: source
contamination, correctly detected — ADR 0006 already ruled out repair
("guessing a codepage per record would be inventing data"), so the four stay
in quarantine.

**State the correction as doctrine, not as an incident: "`_rescued_data` is
NULL" does not mean "source dirt"; the triage question is per reject reason,
not universal.** The instruction to check `_rescued_data` came from the
controller's own dispatch; the implementer went past it, checked the charset
and the byte set, and named the column instead of applying the rule
literally. A document that records only the code's defects and not the
instructions' is not an honest record, so this correction is recorded here as
a correction to the *dispatch*, and folded into
[ADR 0006](adr/0006-bronze-dq-gate-policy.md) as the answer to the column
question it had left open.

### 20.3 The cross-month asymmetry, and its F2 consequence

`correio_eletronico` is not one of the two columns the encoding check covered
when 2026-06 was gated. Timeline, from git:

- `ed004e0` (2026-07-24) — estab rules with the encoding check over
  `nome_fantasia` and `logradouro` only;
- **2026-06 estab run `118868417561350`, 2026-07-28** — gated by that narrow
  check, rejected zero;
- `caed88e` (2026-07-31) — widened the check to U+FFFD over every column,
  which is what caught these four.

So the widened check retroactively implies un-flagged rows in 2026-06's
bronze. It does, exactly:

```

```

The same four companies, the same email lengths — present in 2026-06's
bronze, promoted un-flagged, and they are 2026-06's *only* U+FFFD rows across
every free-text column checked. **This is a rule change, not a source
change**: the encoding check covered 2 of 30 columns until `caed88e`, after
the 2026-06 run, and `promote_batch` re-applies the current rules at promote
time rather than the rules a row was first gated under.

Deciding whether these four belong in bronze is not the operator's call, and
the mechanism enforces that rather than merely stating it: `promote_batch`

not a curiosity:** for these four establishments, a satellite will see a
2026-06 row and no 2026-07 row, and will read that as "unchanged" when the

### 23.2 Three grounds, in ascending force

**(1) The same reason family spans 4,406× across tables.** `6.380e-5 /
1.448e-8` = **4,406**, and both cells are `null_or_empty_<a required name
column>` — the same defect, the same family, two tables. A single threshold set
at socios' rate tolerates `6.380e-5 × 69,062,850` = **4,406 empresas rows**
against an observed load of 1: enough headroom for a genuine parse defect to
pass green, which is the failure mode Decision 3 exists to catch. Set at
empresas' rate instead, socios' allowance is `1.448e-8 × 27,992,378` = **0.41
rows** — absolute gating with extra arithmetic, and socios turns red every month
regardless. `docs/f1.4b-pr-a-run-evidence.md:344-345` had already set the bar
that a threshold must be calibratable per table; the spread is why.

**(2) Only one of three tables has a numerator worth calibrating.** Per-table
thresholds clear PR A's bar arithmetically and fail it statistically:

- **empresas** — numerator 1 in both months, and it is the *same record*
  (`cnpj_basico` 08314885, [§17](#17-empresas--run-371067950667703)). Poisson
  relative error at n=1 is ~100%; the apparent rate change 1.457e-8 → 1.448e-8
  is the denominator growing, not a signal.
- **estabelecimentos** — numerator **0** for the tolerable family in *both*
  months. Its only rejects are `encoding_replacement_char`, which is on the
  never-tolerate list. A threshold cannot be calibrated from an absence.
- **socios** — 1,797 and 1,786, agreeing to 1.2%. Genuinely usable, and the
  only one.

`rules.py` already declines to make `empresas.capital_social` required because
it is "plausibly always filled" and "'plausibly' is not the standard a hard gate
is held to." A threshold derived from n=1 and n=0 is that same standard applied
to the gate's *release valve*, where being wrong fails **open** rather than
closed.

**(3) The per-reason option fails structurally — and this is what decides it.**
A per-reason threshold, tolerating `null_or_empty_*` by rate while keeping
`encoding_replacement_char` at zero, is the option whose evidence position had
genuinely changed and the one the dispatch recommended. It is disqualified by a
property of the gate rather than by any number.

**`_dq_reject_reason` names the first rule that fired, not everything wrong with
the row.** Independently verified in the code:
`dq._reject_reason` (`src/opl/bronze/dq.py:107-116`) builds a first-match-wins
chain — `rescued_data_present`, then the rule set's own order — closing
`.otherwise(F.lit(None))`; and `rules_for`'s contract map
(`src/opl/bronze/rules.py:233-256`) splices `*_required_rules(...)`, which emits
the `null_or_empty_*` rules at `rules.py:105-106`, **ahead of**
`("encoding_replacement_char", ...)` in all four contracts (`:235`/`:236`,
`:239`/`:241`, `:245`/`:247`, `:251`/`:253`).

So a row that is **both** blank in a required column and carrying a lost byte
elsewhere reports the **tolerated** reason. Under a per-reason policy that row
is counted toward a tolerated rate, found under it, and promoted — with a lost
byte, and with no run turning red. **A "never tolerated" reason that a
co-occurring tolerated reason can hide is not a never.** Tolerating
`null_or_empty_*` by rate would wave through, under a tolerated label, the exact
defect [§20.2](#202-the-four-rejects-and-the-triage-doctrine-correction) spent
this phase establishing must never be tolerated.

This is not fixable by reordering: `rules.py`'s own comment block records that
grouping the required-field rules already changed which reason a doubly-
defective estab row reports. Reordering trades one first-match artefact for
another. The precondition is structural — per-reason gating needs per-reason
counts derived from **all** matching rules, and that must ship *before* any
per-reason tolerance, never with it.

### 23.3 The counter-evidence the decision survived

The implementer measured the thing that would have made ground (3) an observed
hazard rather than a latent one, and found against himself. The same
column-by-column scan as §23.1's footnote, reported in full:

```
tbl              | mon     | fffd_any | req_blank | both
empresas         | 2026-06 |        0 |         1 |    0
empresas         | 2026-07 |        0 |         1 |    0
estabelecimentos | 2026-06 |        4 |         0 |    0
estabelecimentos | 2026-07 |        4 |         0 |    0
socios           | 2026-06 |        0 |      1797 |    0
socios           | 2026-07 |        0 |      1786 |    0
```

`fffd_any` — rows carrying U+FFFD in any contract column. `req_blank` — rows
blank or NULL in any `REQUIRED_FIELDS` column. `both` — rows in both sets.

**`both` = 0 in all six cells. The shadowing is latent, not active.** It has
never happened here. The implementer reported this as weakening his own central
argument rather than omitting it, and sustained the disqualification on
different ground: **adopting the option is precisely what would stop anyone
measuring it.** Once `null_or_empty_*` stops firing the gate, the overlap count
above is a number nobody has any cause to run, and the first month it goes
non-zero is the month the never-tolerated check silently stops applying.

That is a judgement about where attention goes, not a proof, and it is stated
as one in ADR 0006 as well as here — it is the softest joint in the decision.
It is recorded at this length because a decision that meets its own
counter-evidence and survives it on stated grounds is worth more than one that
never met any, and because a reader who only sees the grounds and not the
counter-evidence cannot tell which kind they have.

### 23.4 The decision is pinned by a tripwire, not by prose

The task's one code change is
`tests/bronze/test_rules.py::test_a_blank_required_column_hides_the_lost_byte_behind_it`,
parametrised over all three F1.4b contracts (empresas `razao_social` /
`qualificacao_responsavel`; socios `nome_socio_razao_social` / `pais`;
estabelecimentos `municipio` / `correio_eletronico`). It asserts that a
doubly-defective row reports the *tolerated* reason, that it is rejected anyway,
and that a U+FFFD-only row still reports `encoding_replacement_char` — so
assertion 1 pins the *ordering* rather than a broken encoding check.

It is a **tripwire, not a bug report**. The ordering is deliberate; the test's
job is to go red the day someone makes the gate count all matching rules, which
is exactly ADR 0006's condition 1 and the only thing that makes per-reason
gating implementable. Its failure message sends whoever trips it to ADR 0006
rather than to the assertion. Focused run `3 passed, 25 deselected`; full suite
**630 passed, 6 deselected** (baseline 627 + these 3).

### 23.5 What absolute gating costs, corrected rather than inherited

ADR 0006 booked the cost of fail-closed in F1.3 as "a human in every run",
measured on a batch-per-part flow where one estabelecimentos ingest was four
batches. That arithmetic no longer holds: it is one batch per table per month
now, and empresas and socios are the only two tables that fire. The measured
cost is **two repromotes per month, one CLI command each**, indefinitely. The
cost did not vanish; the figure behind the original complaint did, and ADR 0006
now says so rather than carrying it forward.

What the price bought, measured rather than asserted: **both** of this phase's
most consequential findings came from the gate firing on a batch whose rate
(5.531e-8) sits below any threshold this ADR would plausibly have set — the
triage-doctrine correction
([§20.2](#202-the-four-rejects-and-the-triage-doctrine-correction)) and the
cross-month F2 modelling hazard
([§20.3](#203-the-cross-month-asymmetry-and-its-f2-consequence)). ADR 0006
flags that this is not decisive on its own — a control cannot be justified
purely by what it incidentally surfaced — but that rate is exactly the argument
a threshold would have used to wave those four rows through.

**A threshold is also not the fix for reclaim, and adopting one to fix it would
be worse.** See [§25](#25-what-this-pr-does-not-settle).

### 24.5 Why the property is rejected

**(1) It is an exhaustive list, and would kill statistics on every other
column.** The Databricks docs state it plainly: *"Statistics aren't used for
columns not included in the current list of statistics columns."*
Setting it to `_batch_id` would make the statistics on `cnpj_basico`, `uf`,
`situacao_cadastral`, `cnae_fiscal_principal` and every other indexed column
**unused** — surrendering skipping on the first 32 columns to buy skipping on a
column that already has it. Avoiding that means enumerating all 33+ columns by
hand and re-editing the list on every schema change, in a table this repository
has already changed the schema of twice (v3 `ADD COLUMNS`, v15 `CHANGE COLUMN`).

**(2) It does not backfill; the mechanism already in force does.** The docs:
*"Updating these properties doesn't automatically recompute statistics for
existing data."* Backfilling would need an explicit `ANALYZE TABLE ... COMPUTE
DELTA STATISTICS`, which this task is forbidden to run and which Predictive
Optimization has already done at v13.

**(3) There is no headroom left to buy.** The treatment arm already prunes 30 of
30 irrelevant files with zero false positives. The best available outcome of
setting the property was "no change"; the realistic ones were "no change" or
"regression per (1)".

### 24.7 Method note — the DBSQL result cache defeats every obvious cache buster

This belongs in the record because the failure is silent and looks like a
spectacular result.

**16 of 24 executions came back cached and had to be discarded.** The first
attempt busted the cache with a unique comment nonce per statement: DBSQL
strips comments before computing the cache key, so rounds 2 and 3 all returned
`result_from_cache: true` with `read_files_count: 0` and `read_bytes: 0`.
`VERSION AS OF 17` and an output-column alias were also cached — the key is on
the **normalized logical plan**, not the text. **It also survives a warehouse
restart.** What finally worked was a column-free conjunct
(`AND current_timestamp() > TIMESTAMP '2000-01-01'`) and a column-referencing
one (`AND _batch_id <> '<nonce>'`).

Every number in [§24.2](#242-the-measurement--29-of-59-files-identical-warm-and-cold)
comes from a statement whose recorded `result_from_cache` is `false`; that field
was checked on all 24 executions. **Had it not been read, this section would
report "0 files, 0 bytes" for the repeats and conclude something absurd.**

That the busters did not disturb the plan was validated by reproduction rather
than assumed: the treatment arm with the `current_timestamp()` conjunct returned
7,606,418 bytes — byte-for-byte identical to the round-1 run that had no such
conjunct — and the cold run with the `<>` nonce returned 7,606,878 bytes, within
460 B of the warm figure, the same order as the control arm's own cold/warm delta
of 512 B (Parquet footer reads).

**Any future performance measurement in this project that does not check
`result_from_cache` will silently produce zeros.**

## 25. What this PR does not settle

[§11](#11-what-this-document-does-not-establish) is the same list scoped to
Task 1 and is superseded by this one at PR level. Where the two disagree, this
section is current.

### 25.1 Reclaim is still unreachable from the flow, and this PR did not fix it

**The defect is wiring, and only wiring.** `reclaim_landing` is
`depends_on: promote`; `promote` is `depends_on: [check_bad_rows, outcome:
"true"]`. **Any batch with at least one reject never reaches reclaim** — and
`repromote_triaged_batch`, the job that promotes the batch which *does* hold the
rows, is `assert_deployed_revision` → `promote`, with **no reclaim task**.
empresas rejects about one row a month and socios 1,786–1,797, so **both fire
the gate every month, indefinitely**. Under the policy
[§23](#23-task-3--the-dq-gating-decision-measured-across-six-cells-and-decided-against)
just confirmed, this is permanent, not transitional.

What is **not** in doubt, after
[§26.1](#261-the-correction-this-documents-own-headline-finding-needed):
`retention.py` deletes correctly when reached. F1.4a proved it on a real UC
Volume against this exact table — 16,743,815,717 B, zero refused, zero failed,
the directory verified empty and the sibling `zips/` verified untouched.
**Nothing about the deletion logic is unproven. Only the wiring is.**

**The storage consequence, stated with the arithmetic it actually rests on.**
[§13.8](#138-for-task-5--the-48-gb-peak) projected a ~48 GB peak (47,971,843,548
B, 2.18× this Volume's demonstrated high of 22,003,959,144 B) for adding one
month with no reclaim at all. The peak this phase actually observed was
**39.71 GB, 1.80×** ([§21.1](#211-estabs-hand-delete-and-the-phases-running-total))
— and that lower figure was **bought by three hand-deletes between groups**
([§19](#19-the-hand-delete-between-groups--an-operator-action-not-reclaim-working)),
an operator standing in for the missing control. So the honest statement is
narrower than "the ~48 GB peak is the floor": **~48 GB is the floor for every
month added if nobody intervenes, and ~40 GB is the floor if an operator hand-
reclaims between groups every month.** Neither is a control, both grow with each
month, and there is no published quota to measure either against. 8.21 GB of
2026-06 residue is deliberately left in the Volume so the debt stays visible.

**The fix is named and unbuilt: a reclaim task on `repromote_triaged_batch`.**
`reclaim_landing` is already guarded independently of the gate — it deletes only
files bronze proves it holds rows of, for that batch — so its real precondition
is "these rows are persisted", which the triage job satisfies at exactly the
point the in-flow promote does. It is specified in
[ADR 0006](adr/0006-bronze-dq-gate-policy.md) and **not implemented, not
deployed, not run**. Do not read this PR as having fixed it.

[§23](#23-task-3--the-dq-gating-decision-measured-across-six-cells-and-decided-against)
also settles what the fix is *not*: **a rate threshold is the wrong fix.** It
lowers only how often the gate diverts the flow; it leaves the two wiring facts
untouched, so every batch that still exceeds the threshold strands exactly as
today — and those are the batches whose landing files sit longest, because a
human is sitting on them. A control that works until it matters is worse than
one visibly broken.

### 25.2 Four 2026-06 estabelecimentos rows that today's rules reject — an F2 modelling hazard

2026-06's bronze holds four rows the current rule set would reject, promoted
before `caed88e` widened the encoding check from 2 columns to 30
([§20.3](#203-the-cross-month-asymmetry-and-its-f2-consequence)). **This is a
rule change, not source drift** — the same four companies are present in 2026-06
and correctly quarantined out of 2026-07.

**The consequence for F2 is a modelling hazard, not a curiosity.** A satellite
built over these two months sees, for these four establishments, a 2026-06 row
and no 2026-07 row, and will read that as **unchanged** when the truth is *the
2026-07 observation was quarantined*. **A satellite cannot distinguish
"unchanged" from "not observed" unless something records the difference** — and
nothing in bronze does today. **This belongs in the F2 handoff, not only here.**

Two questions stay open behind it. Whether the system of record should be
**re-gated when a rule widens** — that is, whether those four should be removed
from 2026-06's bronze — is a policy question this phase surfaced and did not
answer; ADR 0006 records it. And the general form, which is the more dangerous
one: **a reject rate in this repository is a property of a (month, rule set)
pair, never of a month alone**, so any figure in
[§23.1](#231-the-six-cells-re-measured) must be re-derived after every change to
`rules_for`, or discarded.

### 25.3 Predictive Optimization is an undocumented second writer, and has no ADR

[§24](#24-task-6--the-statistics-measurement-rejected-because-the-platform-already-did-it)
established that a Databricks platform service, unprompted and billed, **set a
table property** on `bronze_cnpj_estabelecimentos` and on
`bronze_cnpj_estab_staging`, **backfilled statistics** across the whole table,
and **compacted estabelecimentos staging twice** (18 files → 8, then 42 → 21;
both rows at [§24.1](#241-predictive-optimization-did-it-named-by-a-system-table-rather-than-inferred)).
No operator asked for any of
it. `delta.workloadBasedColumns.deltaFileStatistics` — the property it set —
**appears nowhere in Databricks' documentation.**

This repository reasons in comments and docstrings about which columns are
indexed, how many files a table holds, and what a scan will cost. **A second
writer that nobody models invalidates that entire class of reasoning**, and the
operation's own metric schema (`removed_data_skipping_columns`,
`old_data_skipping_columns`, `new_data_skipping_columns`) shows it maintains a
set over time rather than making a one-shot decision — so it can retract as well
as add.

**This deserves its own ADR and does not have one.** Nothing in the repo tells a
reader that a second writer exists. The interim rule this phase applied, and
applied only to `rows_of_batch`, is: never state a platform-derived physical
fact in the present tense without dating it and naming its owner, and never let
correctness depend on it. That rule has not been applied anywhere else, and no
audit for other comments of that shape has been done.

The one observability surface is
`system.storage.predictive_optimization_operations_history`. It is not monitored,
and deliberately not asserted in a test: a test of Databricks' optimizer
heuristics would fail on a fresh workspace, fail for anyone who disables
Predictive Optimization, and signal nothing actionable when it did.

### 26.8 If a reader trusts this document and is wrong to, where would that happen?

The question this task was required to answer, and the honest list is not short.

1. **In the parts of §16 the correction did not reach.** §16 has been corrected
   in three places and re-checked, but it was wrong once in a way that a careful
   reader had no way to detect from inside it — the enumeration looked exhaustive
   and read as exhaustive. **If one enumeration over "all jobs" was blind to a
   deleted job, others in this document may be too.** Nothing else here rests on
   a jobs-list sweep, but that is an assertion about this document, not a proof.
2. **In the derived totals.** 55,830,826 / 55,827,243 / 3,583 in ADR 0008, and
   144,193,412 throughout, are **sums this task performed**, not numbers any run
   printed. They are flagged as arithmetic where they appear. They reconcile,
   which is weaker than being measured.
3. **In "37 of 39 months".** The 39 is corrected arithmetic over a range recorded
   in 2026-07. **Availability was not re-measured**, and today is 2026-08 — the
   RFB may well have published 2026-08 by now, which would make it 40. Treat the
   count as "at least 37 uningested", not as a current inventory.
4. **In §24's pruning figure — and note §24 never prints "50.8%".** It reports
   **29 files read, 30 pruned, of 59**, so the percentage quoted here is derived
   (30/59 = 50.8%) rather than stated there. Derivable is not the same as stated,
   and a reader following the reference will not find the number, so it is spelled
   out here. It is one table at one moment, on a
   two-month table whose batches happen to segregate perfectly into files. At
   twelve months the ratio would be far better; after an `OPTIMIZE` that mixes
   batches across files it could be much worse. **The direction is robust; the
   magnitude is not a constant and should not be quoted as one.** The same
   applies to the claim that Predictive Optimization *chose* `_batch_id` because
   of `rows_of_batch`'s filters — the operation exposes no reason metric, so that
   is a strong inference and is marked as one.
5. **In §23's decision, at a sample size it was not tested at.** Six cells, one
   calibratable numerator, one reason family observed at scale, and
   `both = 0` everywhere. The decision is right at n=6. **It is not obviously
   right at n=20**, and ADR 0006's reversal condition (six monthly observations
   per table, numerator ≥ 10) is a number this task chose to make "when would
   this change" checkable — defensible, not observed. The argument that adopting
   per-reason gating would stop anyone measuring the overlap is a judgement about
   human attention, not a proof.
6. **In §25.1's storage floor.** "~48 GB per month" is the projection for a month
   added with **no reclaim at all**; the peak actually observed was 39.71 GB,
   and that lower number was bought by **three hand-deletes**. A reader who
   remembers "48 GB is the floor" and not "unless somebody intervenes every
   month" has the wrong model.
7. **In treating a rejection as a measurement.** §24 rejects
   `delta.dataSkippingStatsColumns` **without ever setting it.** The rejection
   rests on two documented properties and on the absence of headroom — not on a
   measurement of the counterfactual, which was forbidden. That is sound, and it
   is not the same thing as having tried it.
8. **In reading "independently confirmed" as "independently measured".** Several
   confirmations in this document are a second query by a second party against
   the same warehouse at a later time. That catches transcription errors and
   stale heads. It does **not** catch a shared wrong premise — which is exactly
   how §16's error survived being written, reviewed, quoted into ADR 0006, and
   re-quoted into a task report before anything caught it.
9. **In the sections nobody has re-read since they were written.** §1–§9 were
   written at Task 1 and have not been re-verified against the workspace since
   Task 5 changed it. Nothing in this pass suggests they are wrong; nothing in
   this pass checked them, either.

**The general form, which this phase earned the right to state:** every number in
this document is a property of a *(state, method)* pair. §23 says it about reject
rates and rule sets, §24 says it about table properties and platform services,
§26.1 says it about enumerations and the jobs that exist when you run them. **A
figure quoted without its method is a figure that has already started to go
stale.**

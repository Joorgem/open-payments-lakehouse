## 1. Why `bronze_cnpj_estab_quarantine` needed migrating at all

Before this migration, `bronze_cnpj_estab_staging` carried 35 columns and
`bronze_cnpj_estab_quarantine` carried 36 — neither carrying
`_snapshot_month` or `_snapshot_ref_date`. That gap is not new: F1.4a
(2026-07-31) added the two columns to `bronze_cnpj_estabelecimentos` alone, so
staging and quarantine were left behind — the module docstring's own
"THREE TABLES AND NOT ONE" block records the measured 35/36-column gap
(`scripts/backfill_snapshot_columns.py:11-21`).

Quarantine's 36 columns are not an accident of this phase — they are F1.3's DQ
gate doing exactly what it was built to do. `databricks/src/dq_gate_batch.py:85`
appends the gate's reject frame with
`bad.write.format("delta").mode("append").saveAsTable(quarantine)`, with no
`mergeSchema`; when the target table does not yet exist, `saveAsTable` creates
it from whatever frame is appended — including an empty one. Quarantine's
complete Delta history has exactly that event as version 0
(`CREATE TABLE AS SELECT`; independently re-confirmed in
[§10](#10-cleanup-reverted-and-redeployed--confirmed-in-the-deployed-state)).
An empty reject frame, at zero rejects, still created the table — which is how
quarantine ended up with 36 columns (staging's 35 plus `_dq_reject_reason`)
with nobody having decided to add a 36th column; it fell out of the gate's own
append path.

Nobody had noticed because nothing had yet forced the mismatch open. This repo
does not write with `mergeSchema` anywhere, deliberately — a schema is a
contract, and a write that widens it unasked is drift discovered later rather
than now. So the mismatch stays invisible until the next estab ingest actually
sends a 37-column stream against 35-column staging, and the gate then tries to
append a 38-column reject frame into 36-column quarantine.

Both directions of that append were probed before Task 1 was dispatched,
specifically to avoid asserting Delta's append semantics from memory. The
probe was a throwaway script, run with `uv run python` against the repo's own
local Delta session factory, `opl.spark.local_session` — `local[2]`,
`spark.driver.memory 2g`, Delta 3.3.1, the same session configuration
`tests/` uses — and lived only in the session scratchpad, not in the repo.
Its two cases mirror the exact shapes at issue: case A a target with **fewer**
columns than the incoming frame (the quarantine hazard: a 36-column table
receiving a wider reject frame), case B a target with **more** columns than
the incoming frame (the repromote hazard: a wider staging/bronze table
receiving a narrower one). Case A's target was emptied with `DELETE FROM`
before the append, deliberately, to mirror `bronze_cnpj_estab_quarantine`
holding 0 rows. Verbatim output, both cases:

```
A: target probe_db.narrow_target has 3 cols and 0 rows
A: RESULT = APPEND FAILED -> AnalysisException: [_LEGACY_ERROR_TEMP_DELTA_0007] A schema mismatch detected when writing to the Delta table (Table ID: aca97315-f5c3-4d8a-a589-5e4193ec99d4).
B: target probe_db.wide_target has 5 cols
B: RESULT = APPEND SUCCEEDED
B:   {'a': 'a1', 'b': 'b1', 'c': 'c1', '_snapshot_month': '_snapshot_month1', '_snapshot_ref_date': '_snapshot_ref_date1'}
B:   {'a': 'a1', 'b': 'b1', 'c': 'c1', '_snapshot_month': None, '_snapshot_ref_date': None}
```

Case A's target is reported as `3 cols and 0 rows` on the same line as the
verdict, which is what makes "it fails even when the target holds 0 rows" a
measured fact rather than an inference — the row count and the failure sit in
the same transcript. `refuse_non_empty_quarantine`'s own docstring
(`scripts/backfill_snapshot_columns.py:271-277`) cites the same error for this
direction: "probed, and it fails against a 0-row target too
(`_LEGACY_ERROR_TEMP_DELTA_0007`)" — an append carrying more columns than its
Delta target raises `AnalysisException`, even against an empty table.

Case B's two result rows show the NULL fill directly, not merely a successful
append: the first row was written with all five columns populated; the
second was appended by a three-column frame and comes back with
`_snapshot_month: None, _snapshot_ref_date: None`. So a target with **more**
columns than its incoming frame does not raise under Delta's schema
enforcement — it appends, and the columns the frame lacks land NULL for those
rows. That is the shape of the repromote hazard this migration also closes:
before quarantine carried the two snapshot columns, a batch corrected and
re-appended through `repromote_triaged_batch` into a wider staging/bronze
table would have gone in two columns short and landed NULL quietly rather
than failing loud.

A separate probe, run during Task 1 itself and quoted in the implementer's own
report, answers a different question: not whether columns are missing or
extra, but whether a same-column-set append arriving in a **different order**
resolves positionally or by name. That question exists because after this
migration staging ends `[..., _snapshot_month, _snapshot_ref_date]` while
quarantine ends `[..., _dq_reject_reason, _snapshot_month,
_snapshot_ref_date]` — the same column set, different order — and the gate's
future reject frame is ordered like quarantine's, not staging's. Probed
locally against Delta (a target created by SQL DDL in one column order,
appended with a same-named frame in a different order via
`mode("append").saveAsTable`):

```
PROBE _snapshot_month   = '2026-07'
PROBE _dq_reject_reason = 'bad_cnpj_basico_length'
PROBE VERDICT: BY NAME
```

`saveAsTable` resolves **by name** (`AppendData.byName`), not by position, so
the order difference is not a hazard — a separate result from, and not a
restatement of, the missing/extra-column probe above.

So the migration closes both directions at once — the 37-into-35 failure that
would stop the next ingest outright, and the 38-into-36 (and narrower-frame)
failures that would stay latent until a dirty row or a repromote actually
exercised them. The module docstring calls the second "the worse one: it needs
a dirty row to appear, so it can stay latent for months after the expensive
ingest that unblocked it" (`scripts/backfill_snapshot_columns.py:19-21`).

**Pre-migration state, measured before any of this ran:** staging held 35
columns with neither snapshot column; quarantine held 36 columns with neither;
the column-set diff at that point showed `quarantine == staging +
_dq_reject_reason` exactly — the arithmetic this section depends on, confirmed
independently in
[§10](#10-cleanup-reverted-and-redeployed--confirmed-in-the-deployed-state).

## 3. Two defects this task found outside its own listed scope

Both would have surfaced later, and more expensively, than they did here.

### 3.1 Constraint DDL was being applied to whichever table the script wrote, not only to bronze

Before `0678e7d`, `_assert_constraints` applied `spec.constraints` — bronze
DDL: `ALTER COLUMN cnpj_basico SET NOT NULL` and
`CHECK (length(trim(cnpj_basico)) = 8)` — to whatever table `main` had just
written, unconditionally. Once a third argument let that target be staging or
quarantine, an original `--staging` run would have finished `DONE`, printed
`re-asserted 3 constraint statement(s)`, and left the constraint sitting on
staging.

That is a landmine, not a no-op: `opl.bronze.rules` declares
`null_or_empty_cnpj_basico` and `bad_cnpj_basico_length` because rows like that
arrive — into staging, which is exactly where the DQ gate expects to catch and
reject them. A `NOT NULL`/`CHECK` planted on staging would instead fail the
next ingest's Delta write for precisely the row the gate exists to route into
quarantine. The RED-phase test reproduced the pre-fix code issuing those three
statements without error against today's estab data:

```
def test_no_constraint_ddl_is_issued_against_staging_or_quarantine(tbl, capsys):
    ...
>       assert spark.statements == []
E       AssertionError: assert ['ALTER TABLE...asico)) = 8)'] == []
---------------------------- Captured stdout call -----------------------------
backfill: re-asserted 3 constraint statement(s) on workspace.default.bronze_cnpj_estab_staging
```

Today's estab data satisfies both statements, so a `--staging` run under the
original plan would have gone green and the damage would only surface whichever
month first produced a dirty `cnpj_basico` — the same "latent is worse than
loud" shape as the append hazard in [§1](#1-why-bronze_cnpj_estab_quarantine-needed-migrating-at-all).

Fixed in `0678e7d` by scoping the DDL to fire only when the resolved table
equals `DEFAULT.table(spec.bronze)`; on staging or quarantine the script
instead prints why the statements were **not** issued (quoted live in
[§6](#6-the-quarantine-run) and [§7](#7-the-staging-run--71874448-rows)).

### 3.2 The DONE line claimed a new Delta version unconditionally, even on a run that committed nothing

`1d72a1b`'s own fix — skip the write when there are no rows to fill — broke the
final `DONE` line as an unintended consequence, found and fixed in the same
round. On a **repeat** over an already-migrated 0-row target, `missing_columns`
is also empty, so there is no `ALTER` either and the run commits nothing at
all. The unfixed line would have named the pre-run baseline `version` as "the
way back" — a version nothing this run superseded.

That is exactly the shape of F1.4a's real incident: a Databricks
`INTERNAL_ERROR` retried the backfill task past `max_retries: 0` and produced a
second attempt whose own printed "the way back" version was likewise
post-baseline rather than the true rollback target — `docs/f1.4a-migration-evidence.md`,
§7.2 ("The failure triggered a retry past `max_retries: 0`"). That document
records the operator-facing cost of exactly this shape — a printed version
number that is not the way back, read right at the moment it matters most.

Fixed with a conditional keyed on `wrote or to_add` (later extracted into
`_done_line` in `c757d94`); the happy-path string stayed byte-identical to what
`docs/f1.4a-migration-evidence.md` quotes.

which Databricks may run on its own for a managed table. This is a rollback
window, not an archive; everything downstream now depends on the migrated
state, so this window should not be planned around as a way back.

### Gate item 3 — specified against a state that could not exist yet

The controller's own hard-stop for this gate item required the column-set diff
between staging and quarantine to return exactly one row, checked at this
point in the sequence — after quarantine's migration, before staging's. That
condition is unsatisfiable here by construction: quarantine already carried
the two snapshot columns and staging (still 35 columns) did not, so the diff
necessarily returns three rows, not one, until staging is migrated too.

Run at this point:
```sql
SELECT 'quarantine_not_staging', column_name FROM (...)   -- see §8.3 for the full query
```
```
gap                    | column_name
-----------------------+-------------------
quarantine_not_staging | _dq_reject_reason
quarantine_not_staging | _snapshot_month
quarantine_not_staging | _snapshot_ref_date
(3 row(s))
```
```sql
SELECT count(*) AS n_columns FROM workspace.information_schema.columns
WHERE table_schema='default' AND table_name='bronze_cnpj_estab_staging'
```
```
n_columns
---------
35
(1 row(s))
```

The value matched the predicted intermediate exactly: `staging_not_quarantine`
0 rows (staging has no column quarantine lacks), `quarantine_not_staging`
exactly 3 (`_dq_reject_reason`, permanent, plus the two columns staging's own
run was about to add), and 35 + 1 + 2 = 38 — the quarantine column count
measured above. A fourth column, or any `staging_not_quarantine` row, would
have been a real trip.

The implementer proceeded rather than reporting BLOCKED, on the ground that
every value seen was derivable in advance from measurements already in the
brief (staging 35, quarantine 36 → 38), and that reporting a condition that
cannot be satisfied at this point in the sequence as a blocker would describe a
problem that does not exist. That is the process finding worth keeping for its
own sake: a verification step can be specified against a state that is
unreachable in the actual run order and still read as authoritative on the
page — nothing about the check's wording flags that it was evaluated at the
wrong point. The one-row condition was checked again in its correct position,
after both migrations, and it held — see
[§8.3](#83-the-column-set-diff--in-its-correct-position-after-both-migrations).

## 9. UC planned the staging overwrite as a table REPLACE, not `OverwriteByExpression`

```sql
SELECT version, operation FROM (DESCRIBE HISTORY workspace.default.bronze_cnpj_estab_staging) ORDER BY version
```
```
version | operation
--------+-----------------------------------
0       | CREATE TABLE
1       | STREAMING UPDATE
2       | STREAMING UPDATE
3       | SET TBLPROPERTIES
4       | COMPUTE STATS
5       | ADD COLUMNS
6       | CREATE OR REPLACE TABLE AS SELECT
(7 row(s))
```

Version 6 is `CREATE OR REPLACE TABLE AS SELECT`, with
`"isV1SaveAsTableOverwrite":"true"` in its `operationParameters`.
`_assert_constraints`' own docstring documents this branch as unknowable from
the client — which of `OverwriteByExpression` (keeps metadata) or
`AtomicReplaceTableAsSelect` (drops CHECK constraints and NOT NULL) Unity
Catalog picks for `mode("overwrite").saveAsTable` "is not observable from here
without running it against the workspace." This run is what ran it against the
workspace, against a real 71.9M-row managed UC table: **UC picked the
replace.**

Table properties survived it:

```sql
SHOW TBLPROPERTIES workspace.default.bronze_cnpj_estab_staging
```
```
delta.enableDeletionVectors                    | true
delta.enableRowTracking                        | true
delta.parquet.compression.codec                | zstd
delta.workloadBasedColumns.deltaFileStatistics | `_batch_id`
... (15 row(s))
```

`delta.workloadBasedColumns.deltaFileStatistics` was set in version 3
(`SET TBLPROPERTIES`) and survived version 6's replace intact. Staging carries
no CHECK constraint and no column mask, so nothing was lost here, and
`_assert_constraints`'s skip on staging ([§3.1](#31-constraint-ddl-was-being-applied-to-whichever-table-the-script-wrote-not-only-to-bronze))
cost nothing.

**The consequence, stated plainly:** a CHECK constraint, a NOT NULL, and a UC
column mask are not table properties, and are not carried through a replace the
way the property above was. Quarantine's complete history is two versions —
v0 `CREATE TABLE AS SELECT`, v1 `ADD COLUMNS` — with no third, write-shaped
commit ([§6](#6-the-quarantine-run)). So on the one target where
`fill_and_overwrite` ([§3.2](#32-the-done-line-claimed-a-new-delta-version-unconditionally-even-on-a-run-that-committed-nothing))
skips the write entirely, no replace happened: **the 0-row skip prevented a
real table replace, not a hypothetical one.** Had the pre-fix behavior in
either §3.1 or §3.2 reached a masked or constrained non-bronze target, this is
the mechanism that would have executed against it.

This is now a measured, durable fact about how this repository's overwrites
behave against a managed UC table — not only about this migration. Whether it
deserves its own ADR, and whether it graduates beyond this run-evidence doc, is
an open question left for Task 7 to decide; it is recorded here rather than
left to be re-derived.

### 12.3 The retry that should not have happened

`assert_deployed_revision` declares `max_retries: 0`, and the platform ran it
twice anyway against the same run — `attempt 0` then `attempt 1`, both
`FAILED`. The cause: an uncaught exception leaves the task's lifecycle state
`INTERNAL_ERROR`, and `max_retries` governs clean task failures, not
`INTERNAL_ERROR` — a fact this repo already carries, in
`docs/adr/0008-pii-masking-socios.md:143` and in
`docs/f1.4a-migration-evidence.md`, §7.2 ("the failure triggered a retry past
`max_retries: 0`"), but never before observed on a task whose entire job is to
refuse.

It is harmless here, and the reason is structural rather than lucky: the guard
reads two strings and writes nothing, so it is idempotent by construction and
refused identically on both attempts. The durable consequence is not scoped to
this one guard: **any task placed first in a job as a guard must be
side-effect-free**, because `max_retries: 0` will not protect a task that
writes something and then gets retried by the platform against its own
declared setting.

### 12.4 Filename caching — ruled out by measurement

`pyproject.toml` declares a static `version = "0.0.0"`, so the wheel filename
(`open_payments_lakehouse-0.0.0-py3-none-any.whl`) never changes across
rebuilds. The concern: if serverless caches an install by filename, a redeploy
could leave the **old** stamped wheel installed under an unchanged name, and
every guarded job would refuse permanently — a state indistinguishable from a
broken guard.

The discriminator is `opl_smoke`, which reads `built_revision()` from the same
wheel, the same `environment_key` and the same
`dependencies: ["../../dist/*.whl"]` glob as every guarded task, and cannot
refuse because it carries no guard. Two runs bracket the second deploy: run
`136918510113031` reported
`built_revision='2396af361702f645f51dab5d201f1c8271cf0952'` before it, and run
`796168381085213` reported
`built_revision='109ac6eee6550d4fd7c2f74d4c72a089177de38b'` after it — the same
wheel filename, different content read back both times. No caching, so no
`dist/` emptying and no version bump were needed. This is a second reason
`opl_smoke` stays deliberately unguarded rather than merely exempt: it is the
one job that can answer "what is actually installed" without itself being
subject to the question it would need to answer.

### 12.5 A distinction claimed, then retracted

The controller's dispatch for this step asked for confirmation that the
wrong-revision refusal message is distinguishable from a stale-deploy message.
It is not, and cannot be: `_refuse_the_mismatch` branches on what the deployed
value **is** — a well-formed object name that fails to match — and a
genuinely stale deploy and an operator's mistyped `--params revision=`
produce exactly that shape. From inside the run both are the same fact,
expected != actual, and nothing reachable from a job can see the operator's
repository to tell them apart. The message is written accordingly, as a hint
rather than a determination — "The likeliest cause is the simplest" — naming
both revisions and stating a likeliest cause without asserting it.

The implementer's own report had implied, in its Step 6 planning notes, that
the message could make this distinction; the report retracts that in the same
section the live refusal is quoted in, rather than treating it as a limitation
discovered late. It is the second controller-authored specification defect
found this phase — the first was the verification gate specified against a
state that could not exist yet, already recorded in
[Gate item 3](#gate-item-3--specified-against-a-state-that-could-not-exist-yet).
In both cases the implementer reported the mis-specification instead of
manufacturing a result that would have satisfied it as written.

an oversight: the `+dirty` path stays proven locally, through real
`uv build --wheel` invocations reading the stamp out of the built wheel
(fix round 1), and unobserved in the workspace.

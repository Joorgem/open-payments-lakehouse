# F1.3 Estabelecimentos — Real Run Evidence

Real deploy and staged runs of the `bronze_cnpj_estabelecimentos` job
(Databricks Asset Bundle target `free`) against the real RFB Estabelecimentos
parts for `2026-06` — the multi-gigabyte half of the CNPJ snapshot. Host names,
org/workspace IDs and full `run_page_url`s are redacted; run ids, task states
and stdout are verbatim.

**Outcome: 71,874,448 rows of real merchant-grain data in Delta, all 10 parts,
gate clean, and every record the reader had damaged now correct.** Stated
precisely, because the distinction is the whole point: **two** parsing defects in
our own reader silently corrupted rows that passed every quality rule, and both
were fixed and the table rebuilt from the landing zone — the four records broken by
one and the 11,631 broken by the other were re-verified against an independent
parser afterwards. What remains is one record carrying a byte `cp1252` cannot
decode, which Java replaced silently: that character is lost and the gate does not
look for it. So: zero parse-damaged records, one known encoding-damaged one, and
the caveats at the end name what could still hide.** Getting there cost three separate incidents,
two of them platform defects that produced no error at all, and one silent
data-corruption bug in our own reader. All three are documented below with their
forensics, because they are the interesting part — the happy path is four lines
of stdout.

## Job

- Bundle resource key: `bronze_cnpj_estabelecimentos`
- Job name on the workspace: `opl-bronze-cnpj-estabelecimentos` (target `free`,
  mode `development`, so the deployed name is prefixed `[dev <user>]`)
- Five tasks, batch-scoped: `unzip` → `ingest` → `dq_gate_batch` →
  `check_bad_rows` (condition) → `promote` (`outcome: true`) /
  `fail_on_dq` (`outcome: false`)
- Batch scoping is F1.3's evolution of F1.2's whole-table gate: gate and promote
  both filter `_batch_id == run_id`, so a bad row fails its own run instead of
  wedging every later one.
- Companion operator job `repromote_triaged_batch` (ADR 0006) exists because of
  incident 2 below.

## Why the giants land as ZIPs

`databricks-sdk` 0.40 — the pin in force during this phase — capped a single-PUT
upload at 5 GiB, and part 0's inner CSV is 6,780,467,695 B (6.78 GB)
uncompressed, so parts are uploaded compressed and unzipped **on** Databricks, in
the Volume, by the job's first task. Real sizes for `2026-06`: part 0 =
2,128,818,559 B; parts 1–9 ≈ 320–370 MB each.

## Incident 1 — an upload that landed short and said nothing (runs 1, 2)

`unzip` failed with a traceback that pointed nowhere useful:

```text
File "/.../opl/bronze/unzip_volume.py", line 59, in _unzip_one
    with z.open(info) as src, open(tmp, "wb") as out:
File "/usr/lib/python3.12/zipfile/__init__.py", line 1633, in open
    fheader = zef_file.read(sizeFileHeader)
File "/usr/lib/python3.12/zipfile/__init__.py", line 823, in read
    self._file.seek(self._pos)
OSError: [Errno 22] Invalid argument
```

`ZipFile(...)` had succeeded and `infolist()` had returned exactly one member.
The break came only at `z.open(member)`.

**First hypothesis, wrong.** Volumes are a FUSE mount; FUSE serves sequential
reads but might reject `zipfile`'s backward seek to a member header. That fit,
so the zip was staged to local disk before opening — and **run 2 failed
identically**, from local disk. The hypothesis was disproven by the fix meant to
confirm it, and the staging change was reverted rather than left in the tree.

**Actual root cause.** The object in the Volume was the wrong size:

| | bytes |
|---|---|
| local source (size-verified against the WebDAV manifest) | 341,333,959 |
| object landed in the Volume | 273,373,127 |
| **missing** | **67,960,832** (= 1037 × 64 KiB) |

A ranged `GET` on the remote object showed its **tail intact**: a valid EOCD at
EOF with `entries=1, size_cd=76, offset_cd=341,333,861` — the *original* offsets
— plus the real central-directory record. So not a tail truncation, which would
have destroyed the EOCD. CPython then computes

```text
concat = ecd_location - size_cd - offset_cd
       = 273,373,105 - 76 - 341,333,861
       = -67,960,832
```

and shifts every entry's `header_offset` by `concat`. The shifted `start_dir`
lands on the real central directory, so the constructor and `infolist()` both
succeed; the member's `header_offset` is now **negative**, and `z.open()` seeks
to a negative position — `EINVAL`.

**What was actually missing, and why.** The arithmetic above is equally
consistent with a dropped *prefix* and with a gap in the *middle* — both leave
the EOCD intact and shift the central directory by the same amount — and the
head of the object was never read before it was deleted, so the observation alone
cannot separate them. The mechanism can: this is a known bug in the pinned SDK.
In `databricks-sdk` ≤ `0.41.0`, `_BaseClient._perform` rewinds the request body
only inside its `if error is not None` branch, so a raised `ConnectionError` or
`Timeout` — what a multi-minute PUT actually hits — skips the rewind. `retried()`
then re-sends from the offset where the stream had failed, and `requests`
recomputes `Content-Length` as `st_size - tell()`. The retry is therefore a
complete, well-formed PUT *of the remainder*: the server stores it and returns
204, and `upload()` returns normally. The object is `original[67960832:]` — a
dropped prefix of exactly the bytes the first attempt had already streamed, which
is why 341,333,959 − 67,960,832 lands precisely on the observed 273,373,127.
Fixed upstream on 2025-01-30 by
[databricks-sdk-py#878](https://github.com/databricks/databricks-sdk-py/pull/878),
released in `0.42.0`, and filed under *Internal Changes* — which is why it never
looked urgent. Reproduced deterministically against four SDK versions with a fake
Files API: `0.40.0` and `0.41.0` short-write silently, `0.42.0` and `0.122.0` do
not.

Two details worth keeping: a clean tail-truncation of the same file raises
`BadZipFile` instead, which is why unit tests over well-formed tmp zips could
never have caught this shape; and **`w.files.upload()` raised nothing** — the
PUT returned as if it had succeeded.

**Fixes, both directions of the same hole:** `upload_to_volume` now reads the
remote `content_length` after every PUT, raises `UploadIntegrityError` on a
mismatch, and deletes the remote object on any failure so a bad upload cannot
leave a readable half-written file; `unzip_volume` rejects a negative
`header_offset` with a message naming the archive and the cause instead of dying
inside `zipfile`.

**That verification has already earned its place**: it later caught two
short-written uploads of part 0 automatically (below), each of which would
otherwise have burned another run exactly like these two.

## Incident 2 — the gate blocked 9.5M good rows over 1 rejected one (runs 5, 6)

Run 5's gate rejected exactly **1** row of 9,506,871; run 6 rejected **3** of
9,506,873. Both reject sets carried the same reason, `bad_cnpj_basico_length`,
and the same signature — a `cnpj_basico` of `'";"02"'`, six characters of
punctuation, with the following fields shifted (a date sitting in `cnpj_ordem`).

The gate did exactly what it was designed to do. The problem was what came
next: promotion is blocked for the whole batch, and a later run ingests new
files under a **new** `_batch_id`, so the blocked batch is never revisited.
9,506,870 good rows had nowhere to go — not a policy choice, a dead end.

Two things came out of it, both recorded in ADR 0006:

- `repromote_triaged_batch`, an operator job that runs the promote step alone
  against an explicitly named batch, after a human has read the quarantine. It
  is not a bypass: it reuses `promote_batch`, which re-applies the same rules
  and appends only passing rows. Both stranded batches were recovered with it.
  One note for anyone checking this against git history: the recoveries ran from
  a working tree before the job was committed, so the commit timestamp is later
  than the runs it describes.
- The measured reject rate — 4 in 42.8M, about 1 in 10.7 million, recurring in
  half the batches — makes zero tolerance impractical: a scheduled ingestion
  would stop for manual triage on most runs. Rate-based gating is specified for
  F1.4 rather than swapped in at the close of this phase.

## Incident 3 — our own reader was silently corrupting records

The rejects from incident 2 were not dirty source data. They were the
**shadow of a parse defect in our reader**, and finding that out is the most
valuable thing in this phase.

Streaming the same inner CSVs out of the local zips with Python's `csv` module
(same dialect: `;`, `"`, cp1252, `newline=''`):

| part | records | field-count deviations | records with an embedded newline | undecodable bytes |
|---|---|---|---|---|
| Estabelecimentos6 | 4,753,435 | 0 | **1** | 0 |
| Estabelecimentos8 | 4,753,435 | 0 | **3** | 1 |

RFB ships records with **literal newlines inside quoted fields** — valid CSV per
RFC 4180 §2.6. Verbatim from the scan:

- part 6: `nome_fantasia = 'RIZZ CAMPOLIM\n'`
- part 8: `complemento = 'ANDAR 16 TORRE 2 SALA 2\n'`,
  `nome_fantasia = 'LOTISA VEREDAS EMPREENDIMENTOS IMOBILIARIOS SPE LTDA\n'`,
  `nome_fantasia = 'RESIDENCIAL LIKE BOA VISTA LTDA\n'`

Spark's CSV reader defaults to `multiLine=false` and split each of those records
in two:

- a **parent** carrying the leading fields with the tail NULL — measured at 18
  of 30 columns lost — which satisfies every key DQ rule (`cnpj_basico` present
  and 8 chars, `cnpj_ordem`, `cnpj_dv` present) and was therefore **promoted**;
- a **fragment** starting mid-field, whose garbage `cnpj_basico` the gate caught.

The counts line up exactly: 1 and 3 embedded newlines per file, 1 and 3
quarantined fragments, 1 and 3 promoted rows missing their trailing fields.

**The trap.** The split adds a row and quarantining the fragment removes one, so
bronze held exactly 4,753,435 rows per part — the *correct* count — with a
damaged record inside it. No row-count reconciliation could have caught this.
The gate was catching the shadow; the actually-corrupted row passed.

Fix: `multiLine=true` in the shared `csv_read_options()`, applied to both
streams and the local batch reader (ADR 0005 records why it was not scoped to
one call site, and the file-level parallelism ceiling it costs).

## Part 0 — the SDK could not upload it, the CLI could

Part 0 (2,128,818,559 B) took four attempts to reach the Volume. The two SDK
attempts that completed a PUT landed **the same wrong byte count**:

| attempt | path | landed | missing |
|---|---|---|---|
| 1 | `databricks-sdk` 0.40 `files.upload` | 757,297,535 | 1,371,521,024 |
| 2 | `databricks-sdk` 0.40 `files.upload` | 757,297,535 | 1,371,521,024 |
| 3 | `databricks fs cp` (CLI v1.8) | **2,128,818,559** | — |

Byte-identical truncation twice is deterministic, not a flaky link, so retrying
was abandoned rather than repeated. Both bad attempts were caught by the post-PUT
size verification from incident 1 and the partial object deleted automatically —
without it, the next run would have failed exactly like runs 1 and 2.

Switching to the CLI worked on the first try, which narrows the defect to the
**old SDK's single-PUT path**: not the network, and not the 5 GiB ceiling. It
rests on one CLI success against two SDK failures, so a server-side defect in
handling >2 GB single-PUT bodies fits the same evidence — what is solid is that
the truncation was byte-identical twice, i.e. deterministic, and that a
different client path moved the same file intact. `databricks-sdk` is pinned at `0.40.0` here while
the retry-rewind bug behind incident 1 is fixed from `0.42.0`, and from
`0.72.0` the SDK multiparts by default — anything above
`files_ext_multipart_upload_min_stream_size` (50 MiB) goes out as presigned parts
with configurable parallelism — with the 5 GiB figure surviving there only as an
Azure-firewall-specific cap. None of that exists in 0.40. Upgrading is therefore
the fix for both upload incidents in this phase, and it is filed as a
carry-forward rather than done here: it changes the constraint this phase's
architecture was designed around, which is a decision for the start of a phase,
not the end of one.
Two consequences: evaluating that upgrade is now a backlog item, and the
"single PUT, non-resumable" constraint recorded as a durable design fact is a
property of the pin rather than of the platform.

> **Carry-forward discharged in F1.4, and the decision this section deferred has
> been made — see [ADR 0007](adr/0007-multipart-upload.md).** The pin is now
> `databricks-sdk>=0.123.0,<0.124.0`, so the retry-rewind bug behind incident 1
> is fixed at the source rather than only caught after the fact by the post-PUT
> size check — which stays, as defence in depth. Every claim in this document
> that attributes the 5 GiB single-PUT ceiling to the *Files API* is wrong: it
> was the 0.40 client's ceiling. Read those sentences as describing what the code
> believed during F1.3, not what is true now — under multipart there is no
> single-PUT ceiling at all.
>
> **The paragraph above is also wrong about when multipart landed.** Measured
> against the published wheels: `FilesExt` first overrides `upload` at **0.45.0**,
> gated on `multipart_upload_min_stream_size` — 5 MiB then, raised to 50 MiB and
> renamed `files_ext_multipart_upload_min_stream_size` at 0.72.0. So 0.72.0 did
> not introduce multipart-by-default; it *raised the floor* on a path that had
> already been the default for 27 minor releases, and 0.71.0 has no size gate at
> all. 0.44.x is the last line where `FilesExt` overrides only `download`. Our
> objects are 320 MB–2.13 GB, far above every one of those thresholds, so on any
> SDK from 0.45.0 onward every upload here is multipart regardless. ADR 0007
> carries the full bisect.

**Run 8 also settled ADR 0005's open question.** Part 0's inner CSV is 6.78 GB,
and with `multiLine=true` Spark cannot split a file across tasks — so this was
the single-huge-file case the ADR flagged as untested. It read, parsed and wrote
29,093,533 rows in a run lasting about nine minutes. The parallelism ceiling is
real but not a problem at this scale; no pre-splitting is needed.

## Incident 4 — half of RFC 4180, found after four review passes had approved the branch

Incident 3 fixed §2.6 of RFC 4180 — newlines inside quoted fields. Nobody checked
**§2.7**: a quote inside a quoted field is escaped by **doubling** it. Spark's
`escape` option defaults to backslash, so RFB's `""` was never unescaped, and with
`unescapedQuoteHandling` at its default the affected values kept their literal
quotes and could absorb the `;` delimiter along with the following field's quotes.

A real record from part 6, verbatim:

```text
"09516882";...;"140";": ""A"";";"DUCILIA CARONE";"36520000";"MG";...
```

| field | Python's `csv` (and RFC 4180) | what bronze held |
|---|---|---|
| `complemento` | `: "A";` | `": ""A""` |
| `bairro` | `DUCILIA CARONE` | `";"DUCILIA CARONE"` |

The `bairro` value is the delimiter and the next field's quotes swallowed whole.

**Why this is not a cosmetic edge case.** RFB uses `;` as an *internal* separator
inside `complemento` — `QUADRA 07;BLOCO 702A;APT 201` — in 6,261 of 107,363
records sampled, about 5.8%. Correct quoted-field parsing is load-bearing at that
rate, so a defect that lets a value absorb the delimiter is worse than it looks.

Measured, before the fix:

| measurement | value |
|---|---|
| records in the first 107,363 of part 6 carrying a quote inside a field | 13 |
| of those, differing from Python's `csv` | **13 of 13** |
| the same, with only `escape` added | **0 of 13** |
| records in part 6 whose double-quote count deviates from 2×30 | 461 of 4,753,436 |
| rows in the 71.9M bronze table holding a literal `""` in a free-text field | **11,631** |

After the fix and the rebuild (run 9): **17**. Those 17 are not residue — they are
faithful. Checked against Python's `csv` straight out of the zips:

```text
cnpj 64804511  nome_fantasia = '"PIT STOP SOUND SYSTEMS""'
cnpj 00841153  nome_fantasia = 'LANCHONETE BIRO""S BAR'
```

Byte-identical to what bronze now holds. There is a snack bar named `BIRO"S BAR`,
and the register stores the quotes doubled; two independently written parsers agree
on the value. Some of the 17 carry an *odd* number of quotes, which is strictly
malformed CSV — those were the ones worth checking, and Spark's reading of them
matches the reference implementation too.

**Three things about this one are worth more than the fix.** It was **pre-existing
since F1.2** and independent of incident 3 — output was byte-identical with
`multiLine` on and off across all 30 fields of 107,363 records. It survived four
review passes (per-task reviews, two fix rounds, a whole-branch review, and
CodeRabbit), because reading the diff cannot reveal an option that was never
written; it took reading the specification and then the real bytes. And it belongs
to the same silent class as incident 3: every DQ rule passes, the row count
reconciles, and the row is promoted.

Two decisions taken while fixing it, both by measurement rather than reflex:

- **`unescapedQuoteHandling` was deliberately not added.** A matrix over
  `{escape only, + STOP_AT_CLOSING_QUOTE, + BACK_TO_DELIMITER, + RAISE_ERROR}`
  produced byte-identical correct output on every well-formed input — the setting
  is inert once `escape` is right. The variants diverge only on malformed input,
  where none matches the reference and `RAISE_ERROR` would abort the job. A test
  now asserts the option stays absent.
- **F1.2's lookup stream shares this reader**, so the golden lock had to be
  re-established by measurement, not assumption: all six real lookup files were
  read with and without `escape` and compared field-by-field — identical, 7,408
  rows, which is exactly F1.2's golden count. The reason it is inert there is that
  every lookup record has exactly four double quotes, none inside a value.

A latent second defect fell out with it: the inherited backslash `escape` also
corrupts any value *ending* in `\`, which would consume the closing quote and run
into the next record. Part 6 contains 39 backslash bytes and zero `"` sequences,
so it had never fired.

## Operational findings from moving ~4.9 GB for real

- **The SDK's default upload window is 5 minutes** (`retry_timeout_seconds=300`),
  a *total* budget for one call across all attempts. The subtlety: the deadline
  is only checked **between** attempts, so it never interrupts a PUT in flight —
  it makes the first retryable failure fatal once spent. `Estabelecimentos3.zip` (366,824,247 B) died with
  `Timed out after 0:05:00`. Note what that does **not** mean: a PUT that never
  fails is never subject to the deadline no matter how long it runs, so duration
  alone cannot produce this error. Some attempt failed for an unrecorded reason
  and, at the measured ~67 MB/min upstream, the 300 s budget was already spent —
  so there was no time left to retry it. No size threshold is claimed. The upload client now carries a two-hour budget,
  sized for one attempt of the worst case plus a retry. `http_timeout_seconds`
  was deliberately left at its default — it is a socket read-inactivity timeout,
  and widening it only converts a dead socket into a silent multi-hour hang.
- **A failed PUT may leave nothing, or may leave a corrupt object.** The timeout
  above left no object; the incident-1 interruption left a readable, wrong-sized
  one. Only post-upload verification distinguishes them.
- **The RFB share behaved as if throttled per client rather than per
  connection.** Two concurrent part downloads moved ~11.75 MB/min combined
  against ~10 MB/min for one. That is a single comparison on a server the
  extraction ADR already records as ~50% flaky, so it does not isolate
  throttling from ordinary variance — but the practical conclusion held all
  night: parallelism bought almost nothing, and this phase's wall clock was set
  by the source, not by Databricks and not by the local link, which pushed ~6×
  faster upstream than the RFB served downstream.
- **A `SIGKILL` bypasses the library's cleanup.** `upload_to_volume` deletes the
  remote target on any failure it can observe, but a killed process runs no
  handler at all, so an interrupted PUT can still leave a wrong-sized object
  behind. One interruption did hit mid-PUT here and the Volume happened to stay
  clean, confirmed with `databricks fs ls --long`. Checking the landed size
  before trusting a staged object is therefore a manual step in the operator
  procedure below, not something the library does — being able to repair the
  previous run's mess matters as much as not creating it, and that half is not
  automated yet.

## What this does not prove

- **An ingest that dies partway through is not reconciled by anything.**
  `trigger(availableNow=True)` drains the backlog in several micro-batches, each
  committing to staging *and* to the Auto Loader checkpoint. If the task fails
  after some files have committed, those rows sit in staging under a
  `_batch_id` that will never be gated (so their rejects never reach quarantine)
  and never promoted, while the checkpoint has permanently consumed the files —
  a re-run ingests only what is left, under a new batch id. Nothing in the job
  compares staging to bronze, so the shortfall would be silent. The
  reconciliation above is currently a manual check; making it automatic (or
  keeping a promotion ledger) is F1.4 work.
- **One record in part 8 carries a byte cp1252 cannot decode** (`0x8f`). Python
  raises on it; Java's decoder substitutes U+FFFD silently, which makes that
  character the only in-band evidence a byte was lost. Which column holds it is
  not known, and the encoding rule covers 2 of 30 columns — so whether the gate
  would catch this record is undetermined (ADR 0006).
- **The defect class is not closed, only its known causes.** Two shapes of silent
  parse corruption were found here (RFC 4180 §2.6 and §2.7), the second of them
  only after four review passes had approved the branch. Nothing in the pipeline
  detects the class: no rule flags a row whose trailing tail is NULL, and none
  compares a value against an independent parse. Both were found by reading the
  specification and then the real bytes — which is not a control, it is an
  accident of attention. A completeness or field-count check is the missing
  defence-in-depth layer, and a periodic cross-parser sample would be the control
  that does not depend on someone thinking to look.
- **The test suite's Spark tests need free memory that nothing declares.** On a
  host with ~1.8 GB free, 14 of them fail with a Delta `BlockManager` error that
  says nothing about memory; the same commit passes in CI. The local session is
  built with `local[*]` and default driver memory.
- Verification covered the four damaged records individually plus aggregate
  counts and the cross-parser agreement — not 42.8M rows one by one.

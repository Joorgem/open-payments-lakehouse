# F1.3 Estabelecimentos — Real Run Evidence

Real deploy and staged runs of the `bronze_cnpj_estabelecimentos` job
(Databricks Asset Bundle target `free`) against the real RFB Estabelecimentos
parts for `2026-06` — the multi-gigabyte half of the CNPJ snapshot. Host names,
org/workspace IDs and full `run_page_url`s are redacted; run ids, task states
and stdout are verbatim.

**Outcome: 71,874,448 rows of real merchant-grain data in Delta, all 10 parts,
gate clean, zero damaged records.** Getting there cost three separate incidents,
two of them platform defects that produced no error at all, and one silent
data-corruption bug in our own reader. All three are documented below with their
forensics, because they are the interesting part — the happy path is four lines
of stdout.

## Job

- Bundle resource key: `bronze_cnpj_estabelecimentos`
- Job name on the workspace: `opl-bronze-cnpj-estabelecimentos` (target `free`,
  mode `development`, so the deployed name is prefixed `[dev <user>]`)
- Five tasks, batch-scoped: `unzip` → `ingest` → `dq_gate_batch` →
  `check_bad_rows` (condition) → `promote` (`outcome: true`) /
  `fail_on_dq` (`outcome: false`)
- Batch scoping is F1.3's evolution of F1.2's whole-table gate: gate and promote
  both filter `_batch_id == run_id`, so a bad row fails its own run instead of
  wedging every later one.
- Companion operator job `repromote_triaged_batch` (ADR 0006) exists because of
  incident 2 below.

## Why the giants land as ZIPs

The Files API caps a single-PUT upload at 5 GiB (`databricks-sdk` 0.40) and part
0's inner CSV is ~14 GB uncompressed, so parts are uploaded compressed and
unzipped **on** Databricks, in the Volume, by the job's first task. Real sizes
for `2026-06`: part 0 = 2,128,818,559 B; parts 1–9 ≈ 320–370 MB each.

## Incident 1 — an upload that landed short and said nothing (runs 1, 2)

`unzip` failed with a traceback that pointed nowhere useful:

```
File "/.../opl/bronze/unzip_volume.py", line 59, in _unzip_one
    with z.open(info) as src, open(tmp, "wb") as out:
File "/usr/lib/python3.12/zipfile/__init__.py", line 1633, in open
    fheader = zef_file.read(sizeFileHeader)
File "/usr/lib/python3.12/zipfile/__init__.py", line 823, in read
    self._file.seek(self._pos)
OSError: [Errno 22] Invalid argument
```

`ZipFile(...)` had succeeded and `infolist()` had returned exactly one member.
The break came only at `z.open(member)`.

**First hypothesis, wrong.** Volumes are a FUSE mount; FUSE serves sequential
reads but might reject `zipfile`'s backward seek to a member header. That fit,
so the zip was staged to local disk before opening — and **run 2 failed
identically**, from local disk. The hypothesis was disproven by the fix meant to
confirm it, and the staging change was reverted rather than left in the tree.

**Actual root cause.** The object in the Volume was the wrong size:

| | bytes |
|---|---|
| local source (size-verified against the WebDAV manifest) | 341,333,959 |
| object landed in the Volume | 273,373,127 |
| **missing** | **67,960,832** (= 1037 × 64 KiB) |

A ranged `GET` on the remote object showed its **tail intact**: a valid EOCD at
EOF with `entries=1, size_cd=76, offset_cd=341,333,861` — the *original* offsets
— plus the real central-directory record. Not a truncation: bytes missing from
the middle, tail preserved. CPython then computes

```
concat = ecd_location - size_cd - offset_cd
       = 273,373,105 - 76 - 341,333,861
       = -67,960,832
```

and shifts every entry's `header_offset` by `concat`. The shifted `start_dir`
lands on the real central directory, so the constructor and `infolist()` both
succeed; the member's `header_offset` is now **negative**, and `z.open()` seeks
to a negative position — `EINVAL`.

Two details worth keeping: a clean tail-truncation of the same file raises
`BadZipFile` instead, which is why unit tests over well-formed tmp zips could
never have caught this shape; and **`w.files.upload()` raised nothing** — the
PUT returned as if it had succeeded.

**Fixes, both directions of the same hole:** `upload_to_volume` now reads the
remote `content_length` after every PUT, raises `UploadIntegrityError` on a
mismatch, and deletes the remote object on any failure so a bad upload cannot
leave a readable half-written file; `unzip_volume` rejects a negative
`header_offset` with a message naming the archive and the cause instead of dying
inside `zipfile`.

**That verification has already earned its place**: it later caught two
short-written uploads of part 0 automatically (below), each of which would
otherwise have burned another run exactly like these two.

## Incident 2 — the gate blocked 9.5M good rows over 1 bad one (runs 5, 6)

Run 5's gate rejected exactly **1** row of 9,506,871; run 6 rejected **3** of
9,506,873. Both reject sets carried the same reason, `bad_cnpj_basico_length`,
and the same signature — a `cnpj_basico` of `'";"02"'`, six characters of
punctuation, with the following fields shifted (a date sitting in `cnpj_ordem`).

The gate did exactly what it was designed to do. The problem was what came
next: promotion is blocked for the whole batch, and a later run ingests new
files under a **new** `_batch_id`, so the blocked batch is never revisited.
9,506,870 good rows had nowhere to go — not a policy choice, a dead end.

Two things came out of it, both recorded in ADR 0006:

- `repromote_triaged_batch`, an operator job that runs the promote step alone
  against an explicitly named batch, after a human has read the quarantine. It
  is not a bypass: it reuses `promote_batch`, which re-applies the same rules
  and appends only passing rows. Both stranded batches were recovered with it.
- The measured reject rate — 4 in 42.8M, about 1 in 10.7 million, recurring in
  half the batches — makes zero tolerance impractical: a scheduled ingestion
  would stop for manual triage on most runs. Rate-based gating is specified for
  F1.4 rather than swapped in at the close of this phase.

## Incident 3 — our own reader was silently corrupting records

The rejects from incident 2 were not dirty source data. They were the
**shadow of a parse defect in our reader**, and finding that out is the most
valuable thing in this phase.

Streaming the same inner CSVs out of the local zips with Python's `csv` module
(same dialect: `;`, `"`, cp1252, `newline=''`):

| part | records | field-count deviations | records with an embedded newline | undecodable bytes |
|---|---|---|---|---|
| Estabelecimentos6 | 4,753,435 | 0 | **1** | 0 |
| Estabelecimentos8 | 4,753,435 | 0 | **3** | 1 |

RFB ships records with **literal newlines inside quoted fields** — valid CSV per
RFC 4180 §2.6. Verbatim from the scan:

- part 6: `nome_fantasia = 'RIZZ CAMPOLIM\n'`
- part 8: `complemento = 'ANDAR 16 TORRE 2 SALA 2\n'`,
  `nome_fantasia = 'LOTISA VEREDAS EMPREENDIMENTOS IMOBILIARIOS SPE LTDA\n'`,
  `nome_fantasia = 'RESIDENCIAL LIKE BOA VISTA LTDA\n'`

Spark's CSV reader defaults to `multiLine=false` and split each of those records
in two:

- a **parent** carrying the leading fields with the tail NULL — measured at 18
  of 30 columns lost — which satisfies every key DQ rule (`cnpj_basico` present
  and 8 chars, `cnpj_ordem`, `cnpj_dv` present) and was therefore **promoted**;
- a **fragment** starting mid-field, whose garbage `cnpj_basico` the gate caught.

The counts line up exactly: 1 and 3 embedded newlines per file, 1 and 3
quarantined fragments, 1 and 3 promoted rows missing their trailing fields.

**The trap.** The split adds a row and quarantining the fragment removes one, so
bronze held exactly 4,753,435 rows per part — the *correct* count — with a
damaged record inside it. No row-count reconciliation could have caught this.
The gate was catching the shadow; the actually-corrupted row passed.

Fix: `multiLine=true` in the shared `csv_read_options()`, applied to both
streams and the local batch reader (ADR 0005 records why it was not scoped to
one call site, and the file-level parallelism ceiling it costs).

## Run 7 — the clean rebuild

Records already ingested under `multiLine=false` are not repaired by the fix:
the Auto Loader checkpoint has consumed those files. Bronze is a derived layer
and the landing zone was intact, so it was rebuilt rather than patched — the
three derived tables dropped and the Estabelecimentos checkpoint and schema
locations removed (the F1.2 lookup state deliberately untouched).

`unzip` reported 9 files present and extracted none — all nine matched their

### Verification

**Cross-implementation agreement.** Python's `csv` reads 4,753,435 records per
part; Spark now produces 9 × 4,753,435 = 42,780,915. Two independently written
parsers agree.

**The defect signature is gone:**

| | before | after |
|---|---|---|
| rows | 42,780,915 | 42,780,915 |
| rows with NULL tail (`uf` and `municipio` both NULL) | 4 | **0** |
| rows carrying an embedded newline in a field | 0 | **4** |
| gate rejects | 4 | **0** |

**Field-by-field, source to table.** The four previously damaged records were
traced individually from the raw bytes in the zips to their bronze rows. All
four match, with the newline preserved inside the field as data. One example:

| field | from the zip | in bronze |
|---|---|---|
| `cnpj_basico` / `cnpj_ordem` / `cnpj_dv` | `43074015` / `0002` / `98` | identical |
| `nome_fantasia` | `RESIDENCIAL LIKE BOA VISTA LTDA\n` | `RESIDENCIAL LIKE BOA VISTA LTDA<LF>` |
| `tipo_logradouro` / `logradouro` / `numero` | `RUA` / `DO PRINCIPE` / `144` | identical |
| `bairro` / `cep` / `uf` / `municipio` | `SANTO AMARO` / `50050425` / `PE` / `2531` | identical |

**Rows per source file** — parts 1–9 identical to the row, which is how the
fixed-row-count split of the RFB parts became visible. Part 0 is the remainder
file and carries ~6× the rows of a numbered part:

| part | rows |
|---|---|
| 0 | 29,093,533 |
| 1–9 | 4,753,435 each |
| **total** | **71,874,448** |

## Part 0 — the SDK could not upload it, the CLI could

Part 0 (2,128,818,559 B) took four attempts to reach the Volume. The two SDK
attempts that completed a PUT landed **the same wrong byte count**:

| attempt | path | landed | missing |
|---|---|---|---|
| 1 | `databricks-sdk` 0.40 `files.upload` | 757,297,535 | 1,371,521,024 |
| 2 | `databricks-sdk` 0.40 `files.upload` | 757,297,535 | 1,371,521,024 |
| 3 | `databricks fs cp` (CLI v1.8) | **2,128,818,559** | — |

Byte-identical truncation twice is deterministic, not a flaky link, so retrying
was abandoned rather than repeated. Both bad attempts were caught by the post-PUT
size verification from incident 1 and the partial object deleted automatically —
without it, the next run would have failed exactly like runs 1 and 2.

Switching to the CLI worked on the first try, which localises the defect
precisely: **not the Files API, not the network, not the 5 GiB ceiling — the old
SDK's single-PUT path.** `databricks-sdk` is pinned at `0.40.0` here while
upstream is at `v0.122.0`, whose `files.py` implements parallel **multipart**
upload with part sizing and presigned part URLs, none of which exists in 0.40.
Two consequences: evaluating that upgrade is now a backlog item, and the
"single PUT, non-resumable" constraint recorded as a durable design fact is a
property of the pin rather than of the platform.

**Run 8 also settled ADR 0005's open question.** Part 0's inner CSV is ~14 GB,
and with `multiLine=true` Spark cannot split a file across tasks — so this was
the single-huge-file case the ADR flagged as untested. It read, parsed and wrote
29,093,533 rows in a run lasting about nine minutes. The parallelism ceiling is
real but not a problem at this scale; no pre-splitting is needed.

## Operational findings from moving ~3 GB for real

- **The SDK's default upload window is 5 minutes** (`retry_timeout_seconds=300`),
  a *total* budget for one call across all attempts. The subtlety: the deadline
  is only checked **between** attempts, so it never interrupts a PUT in flight —
  it makes the first retryable failure fatal once spent. At the measured ~67
  MB/min upstream a ~340 MB part sits right at the edge: `Estabelecimentos3.zip`
  (366,824,247 B) died with `Timed out after 0:05:00` while a 336 MB sibling
  finished just inside it. The upload client now carries a two-hour budget,
  sized for one attempt of the worst case plus a retry. `http_timeout_seconds`
  was deliberately left at its default — it is a socket read-inactivity timeout,
  and widening it only converts a dead socket into a silent multi-hour hang.
- **A failed PUT may leave nothing, or may leave a corrupt object.** The timeout
  above left no object; the incident-1 interruption left a readable, wrong-sized
  one. Only post-upload verification distinguishes them.
- **The RFB share throttles per client, not per connection.** Two concurrent
  part downloads moved ~11.75 MB/min combined against ~10 MB/min for one — so
  parallelism buys almost nothing and this phase's wall clock is set by the
  source, not by Databricks and not by the local link, which pushed ~6× faster
  upstream than the RFB served downstream.
- **A `SIGKILL` bypasses the library's cleanup.** One interruption hit
  mid-PUT; the Volume happened to stay clean, but the operator tooling now
  re-checks the remote size before re-uploading — matching size skips, wrong
  size is deleted first. Being able to repair the previous run's mess matters as
  much as not creating it.

## The lookup pipeline was not disturbed

F1.2's `bronze_cnpj_lookup` shares the landing month root, so leakage was a real
risk — a Task 6 probe had already caught that Auto Loader's directory listing is
recursive, which is why the lookup stream carries `pathGlobFilter="*CSV"` while
the Estabelecimentos stream reads its own subdirectory (its inner files end
`.ESTABELE`). Re-checked after these runs, and after the rebuild dropped and
recreated the Estabelecimentos tables and reset only its checkpoint:

```sql
SELECT count(*) FROM workspace.default.bronze_cnpj_lookup   -- 7,408
```

unchanged from F1.2's evidence.

```bash
# environment
export PATH="<WINGET-PACKAGES-DIR>:$PATH"
set -a && source .env && set +a          # DATABRICKS_HOST / DATABRICKS_TOKEN, git-ignored

# deploy + run
cd databricks
databricks bundle deploy -t free --profile opl-free
databricks bundle run bronze_cnpj_estabelecimentos -t free --profile opl-free

# stage a part into the Volume (download is resumable; the PUT is not)
uv run python scripts/extract_giants.py --month 2026-06 --group Estabelecimentos --parts 3 --upload

# verify what actually landed
databricks fs ls dbfs:/Volumes/workspace/default/landing/cnpj/2026-06/zips/estabelecimentos/ --profile opl-free --long

# forensics on a suspect object (ranged read of the tail)
curl -H "Authorization: Bearer <TOKEN>" -H "Range: bytes=<n>-<m>" \
  "<HOST>/api/2.0/fs/files/Volumes/workspace/default/landing/cnpj/2026-06/zips/estabelecimentos/Estabelecimentos1.zip"

# recover a batch after reading its quarantine
databricks bundle run repromote_triaged_batch -t free --profile opl-free --params batch_id=<BATCH_ID>

# rebuild: drop derived tables, reset ONLY the estabelecimentos Auto Loader state
databricks api post /api/2.0/sql/statements --profile opl-free --json \
  '{"warehouse_id":"<ID>","statement":"DROP TABLE IF EXISTS workspace.default.bronze_cnpj_estabelecimentos","wait_timeout":"50s"}'
databricks fs rm -r dbfs:/Volumes/workspace/default/landing/_checkpoints/bronze_cnpj_estab --profile opl-free
databricks fs rm -r dbfs:/Volumes/workspace/default/landing/_schemas/bronze_cnpj_estab --profile opl-free
```

Git Bash on Windows rewrites arguments that look like absolute Unix paths, so
`databricks api` calls need `MSYS_NO_PATHCONV=1` and `databricks fs` needs the
`dbfs:/Volumes/...` form rather than a bare `/Volumes/...`.

## What this does not prove

- **Part 0 is not ingested**, so the `multiLine` parallelism ceiling on a single
  ~14 GB file is untested (ADR 0005).
- **One record in part 8 carries a byte cp1252 cannot decode** (`0x8f`). Python
  raises on it; Java's decoder substitutes U+FFFD silently, which makes that
  character the only in-band evidence a byte was lost. Which column holds it is
  not known, and the encoding rule covers 2 of 30 columns — so whether the gate
  would catch this record is undetermined (ADR 0006).
- **The defect class is not closed, only its known cause.** No rule detects a row
  whose trailing tail is NULL, so a parse break of a different shape would again
  pass fail-closed gating. A completeness or field-count check is the missing
  defence-in-depth layer.
- Verification covered the four damaged records individually plus aggregate
  counts and the cross-parser agreement — not 42.8M rows one by one.

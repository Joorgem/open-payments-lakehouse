# F1.4a Migration — Real Run Evidence

The two workspace migrations of F1.4, executed against the live Free Edition
workspace on **2026-07-31** from branch `feat/f1-4-bronze-generalisation`.

Three things happened, in this order: `bronze_cnpj_estabelecimentos` was
backfilled with the two snapshot columns; the six lookup CSVs were moved into
their own landing subdir and the lookup tables were rebuilt from one clean batch;
and the 16.74 GB of consumed inner CSVs left over from F1.3 was reclaimed.

The lookup reload is the acceptance test for the whole F1.4 refactor. It exercises
the registry, the parameterised ingest, the single gate, the single promote, the
new per-table landing layout and both snapshot columns end to end on real data, at
a scale where every row can be counted by hand.

Host names, org/workspace IDs and full `run_page_url`s are redacted, as in the
F1.2 and F1.3 evidence docs. Run/task ids, batch ids and result states are kept.

**Read [§7](#7-everything-that-did-not-match-expectation) before trusting the
green.** Five things did not match expectation, one of them a real defect in the
backfill script that this run is what found. An evidence doc that only records
successes is not evidence.

**[§7.3](#73-unity-catalog-chose-the-table-replace-plan--but-the-check-constraint-survived-it)
was rewritten after review**, because the first version of it recorded an
observation that had not been made — it read a restoration into a sequence of Delta
operation names without opening the commit properties that contradict it. The
correction is kept in place, with how the error was made, rather than quietly
swapped.

## 2. The Estabelecimentos snapshot-column backfill

### How it was run

`scripts/backfill_snapshot_columns.py` needs the workspace's Spark and this
branch's wheel, so it ran as a job task, not locally. The bundle was deployed
first — without it the job runs the *previously deployed* wheel and the run proves
nothing.

```

Uploading bundle files to /Workspace/Users/<user>/.bundle/open-payments-lakehouse/free/files...
Deploying resources...
Updating deployment state...
Deployment complete!
```

The task was a **temporary** bundle resource,
`databricks/resources/backfill_snapshot_columns_job.yml`, added in `152e35f` and
removed in `9ce5251`. A resource rather than a one-time `databricks jobs submit`
because this is a portfolio repo: a resource is reviewable, re-deployable and
recorded in the deployment state, where a submit exists only in somebody's
scrollback. It was removed because `refuse_contradicting_month` means the script
can now only ever repeat itself, and a deployed button whose sole remaining effect
is to rewrite a 71.9M-row table does not belong beside the real ingestion jobs.

Getting it to deploy needed a second temporary change; see
[§7.4](#74-scripts-is-outside-the-bundle-sync-root).

```
$ databricks bundle run backfill_snapshot_columns -t free --profile opl-free \
    --params table=estabelecimentos,month=2026-06
```

Job run `920475795110362`.

### What it printed — attempt 0 (task run `403532442656154`)

```
backfill: workspace.default.bronze_cnpj_estabelecimentos at version 2
backfill: to undo -> RESTORE TABLE workspace.default.bronze_cnpj_estabelecimentos TO VERSION AS OF 2
backfill: 71874448 rows, month=2026-06, already carries []
backfill: added _snapshot_month, _snapshot_ref_date (metadata-only)
backfill: rows=71874448 (was 71874448) null_month=0 null_ref_date=0 months=['2026-06'] ref_dates=['2026-06-13']
backfill: re-asserted 3 constraint statement(s) on workspace.default.bronze_cnpj_estabelecimentos
backfill: DONE. workspace.default.bronze_cnpj_estabelecimentos is at a new version; version 2 is the way back
```

Exactly the expected line. **The reversibility target is Delta version 2** — the
pre-backfill state, taken before the `ALTER TABLE ADD COLUMNS`, so restoring to it
undoes the columns as well as their values.

**That target has a shelf life.** `RESTORE TABLE ... TO VERSION AS OF 2` works only
while version 2's data files are still on disk, and two things retire them: Delta's
log/file retention (`delta.logRetentionDuration`, `delta.deletedFileRetentionDuration`
— 30 days by default) and any `VACUUM`, which Databricks may also run on its own for
a managed table. So this is a *rollback* window, not an archive. It is academic for
this migration — the post-backfill state is verified good below and nothing wants
undoing — but a reader who finds this doc in three months and reaches for version 2
should expect it to be gone, and should treat `zips/estabelecimentos/` (still intact,
see §4) as the actual way back to the source.

The 71.9M-row overwrite ran **twice**. Why, and why it was harmless, is
[§7.1](#71-a-successful-backfill-was-reported-as-a-failed-run) and

Note the trap the script's own failure message warns about, live in this output:
attempt 1 measured its baseline off what attempt 0 left behind and printed **7**
as "the way back". Version 7 is *post*-attempt-0. The only version that undoes the
backfill is **2**, and it survives only in attempt 0's output and in Delta's
history.

## 4. Reclaiming the 16.74 GB

Those files were promoted before `reclaim_landing` existed, so no live run owns
them. **The ingestion job was deliberately not re-run**: its Auto Loader has
already consumed the zips, so a fresh run would spend 5.26 GB of unzip and read to
produce an EMPTY batch, and `files_of_batch` would correctly return nothing.

> **⚠️ The "EMPTY batch" reasoning no longer holds, 2026-08-03 (F1.4b PR B
> Task 5 Step 0), and the direction it fails in is dangerous.** Auto Loader state
> is now month-scoped, and **no `_checkpoints/2026-06/` exists**. A 2026-06
> estabelecimentos run through the flow today finds an empty checkpoint, treats
> all ten files as new, and produces a **full duplicate batch of 71,874,448
> rows** under a fresh `_batch_id` that the promote's idempotence cannot see.
> Nothing fails; the row counts double. The decision not to re-run was right for
> a different reason than the one given, and it is now right for a much stronger
> one. See `docs/f1.4b-pr-b-run-evidence.md` §14.2.

The real batch ids:

```sql
SELECT _batch_id, count(*) FROM workspace.default.bronze_cnpj_estabelecimentos
GROUP BY 1 ORDER BY 1;
-- ['118868417561350', '71874448']
```

**One id, not several** — the brief anticipated possibly more, so `reclaim_landing`
was invoked once. Via a second temporary resource,
`databricks/resources/reclaim_backlog_job.yml` (added `7f796dd`, removed
`f51ef18`); unlike the backfill it needed no `sync.paths` change, because
`reclaim_landing.py` already lives inside the bundle root.

Before running it, the untested code path was checked rather than trusted.
`fuse_path` had never run against a real Volume, and its failure mode is reporting
every file "already absent" and exiting green having freed nothing — because
`Path("dbfs:/Volumes/...")` is a *relative* path that exists nowhere, so every
unlink would raise `FileNotFoundError`. So the URI form was read first:

```sql
SELECT DISTINCT _source_file FROM workspace.default.bronze_cnpj_estabelecimentos ORDER BY 1;
-- /Volumes/workspace/default/landing/cnpj/2026-06/estabelecimentos/K3241.K03200Y0.D60613.ESTABELE
-- ... nine more, same shape
```

Bare `/Volumes/...`, no `dbfs:` scheme, all ten inside the table's landing dir — so
`fuse_path` passes them through unchanged and all ten resolve as `inside`.

## 7. Everything that did not match expectation

Five items. One is a real code defect, two are Databricks platform behaviours
worth knowing before the next migration, one is a bundle constraint the plan did
not anticipate, and one is a prediction in `task-11-report.md` that turned out to
be wrong.

§7.3 additionally records an error in an earlier draft of §7.3 itself. It is left
visible on purpose: a doc that silently corrects its own overreach teaches the next
reader nothing about how the overreach happened.

### 7.1 A successful backfill was reported as a FAILED run

Job run `920475795110362` printed every expected number and its own `DONE` line,
then reported:

```
Task backfill failed with message: Workload failed, see run output for details.
SystemExit: 0
```
with `life_cycle_state: INTERNAL_ERROR`, `result_state: FAILED`.

**Cause.** `scripts/backfill_snapshot_columns.py` ended with
`raise SystemExit(main())`. That is correct for a local CLI, where `SystemExit` is
the exit code, and wrong for a Databricks `spark_python_task`: serverless executes
the file inside an IPython shell, where `SystemExit` is an *uncaught exception*.
`SystemExit(0)` — success — is therefore surfaced as a workload failure.

Every task in `databricks/src/` already calls `main()` bare, which is why none of
them has ever shown this; the two `scripts/` entry points kept the CLI convention,
and `backfill_snapshot_columns.py` is the one script in `scripts/` that runs on the
workspace.

**Fixed in `28ec99d`** — bare `main()`, with the reason recorded at the call site.
Error handling is unaffected: `main` raises `ValueError`/`RuntimeError` rather than
exiting, which is what carries the numbers into the run output.

**Not re-run to see it green.** Re-running would be a third full rewrite of a
71.9M-row table for zero data gain, and the data outcome is already verified
independently in §2. The fix is unexercised on the workspace, and that is stated
here rather than glossed.

### 7.2 The failure triggered a retry past `max_retries: 0`

The task ran twice — `attempt_number` 0 and 1, task runs `403532442656154` and
`688236401552948`, under one job run, `repair_history: null`. The resource
declared `max_retries: 0`.

`max_retries` governs clean task *failures*. `INTERNAL_ERROR` is a harness-level
error, and Databricks retried through it. So §7.1's cosmetic-looking status defect
had a real consequence: **the 71.9M-row overwrite executed twice.**

It was harmless, and only by design rather than luck of timing:
`refuse_contradicting_month` explicitly permits a repeat with the *same* month, and
the write is idempotent — attempt 1's output shows it taking that path
(`already carries ['2026-06'] ... re-running is idempotent`). Had the second
attempt been given a different month it would have been refused before the write.

The cost was the reversibility target. Attempt 1 printed version **7** as "the way
back", which is post-attempt-0. Only version **2** undoes the backfill, and it now
survives solely in attempt 0's output (recorded in §2) and in Delta's history —
exactly the silent trap `verify_or_raise`'s message warns about, reached here by a
retry nobody asked for rather than by an operator re-running.

**Implication for future one-off writes:** `max_retries: 0` is not sufficient
protection for a non-idempotent job task on this platform. The script's own
idempotence is what protected the data, not the job config.

### 7.3 Unity Catalog chose the table-replace plan — but the CHECK constraint survived it

`task-11-report.md` §4 recorded that `mode("overwrite").saveAsTable` is planned
either as `OverwriteByExpression` (keeps metadata) or `AtomicReplaceTableAsSelect`
(drops CHECK constraints and NOT NULL), that both were observed locally, and that
which one UC picks "is not observable from here". Half of that is now observable:

```
4  CREATE OR REPLACE TABLE AS SELECT
5  CHANGE COLUMN
6  DROP CONSTRAINT
7  ADD CONSTRAINT
```

**Unity Catalog chose the replace plan.** That much the history settles, and it
answers the open question.

**It did NOT drop the CHECK constraint, and an earlier draft of this section said
it did.** That claim was wrong, and the evidence contradicting it is in the table
directly above:

- **v4's own commit properties already carry
  `delta.constraints.cnpj_basico_len8`.** The constraint is present *in the commit
  that replaced the table*, so it was never absent.
- **v6's `DROP CONSTRAINT` records `"existed":"true"`** — it dropped a constraint
  that was there, which is only possible if v4 kept it.
- v4 also records **`isV1SaveAsTableOverwrite: true`**, which is the mechanism:
  the V1 `saveAsTable` overwrite path preserves the table properties, and CHECK
  constraints live in those properties.

So **v5–v7 are `_assert_constraints`'s own churn, not a restoration.** The
re-assert ran, dropped a live constraint, and re-added an identical one. Nothing
was rescued.

How the wrong claim was made, since that matters more than the claim: the
`DESCRIBE HISTORY` query behind the table above selected only `version` and
`operation`. "v4 removed it, v5–v7 put it back" was **inferred from the sequence
of operation names** and then written down as an observation. The commit
properties — `operationParameters`, `operationMetrics`, the `existed` flag — were
never read. A plausible reading of partial evidence was recorded as a finding.

**What is actually supported about `_assert_constraints`:** it remains justified as
**defence in depth**, not as a save. Locally, the replace plan demonstrably *does*
drop constraints — that is what `task-11-report.md` §4 observed and why the
re-assert was written — and nothing about UC's behaviour here is contractual.
Serverless picks a write plan; this run shows which one it picked *today*, on this
table, at this DBR. The re-assert costs one CHECK re-validation and removes the
need to depend on that holding. What it does **not** deserve is the promotion from
"defensive" to "necessary" that this section previously gave it. On this run it was
defensive and nothing more.

**The NOT NULL half is unverifiable either way.** v5's `CHANGE COLUMN` is what the
re-assert emits, and it commits identically whether the nullability it sets was
already in force or not — there is no `existed`-style flag to distinguish them. So
whether the replace preserved NOT NULL is not answerable from this history, and
this doc does not claim it in either direction.

Recorded at this length because it is the failure mode the brief singled out: F1.3's
evidence doc was reviewed by CodeRabbit and found to contain a real internal
contradiction. This was the same failure, one page later, with the contradicting
evidence sitting in the table on the same page.

### 7.4 `scripts/` is outside the bundle sync root

The brief's mechanism — a resource under `databricks/resources/` pointing at
`scripts/backfill_snapshot_columns.py` — does not deploy as written:

```
Error: path C:\...\open-payments-lakehouse\scripts\backfill_snapshot_columns.py
is not contained in sync root path
```

The bundle root is `databricks/` (where `databricks.yml` lives), so `scripts/` is
outside it. `dependencies: ../../dist/*.whl` works because artifacts are uploaded
separately; a `python_file` is not.

Resolved with a temporary `sync: paths: [".", "../scripts"]`, which moves the sync
root to the repo root. The CLI then recomputes every resource's `python_file` for
the new layout (`files/databricks/src/...` instead of `files/src/...`), verified
with `bundle validate --output json` before deploying, and verified back to
`files/src/...` after the revert. Reverted in `9ce5251` together with the resource,
so the permanent jobs do not carry that indirection; the reason is kept as a
comment in `databricks.yml` for whoever next needs to run something from
`scripts/` as a job task.

### 7.5 The reload was NOT smaller than the pre-state — it was identical

The brief expected the reload to be **smaller**, and asked which rows disappeared
and why. **None did.** Pre-state and post-reload are 7,408 rows and identical per
`lookup_type`.

That is not a failure of the reload; the defect it was designed to remove had
never materialised in bronze. `task-11-report.md` §2 predicted live bronze
"plausibly holds 7,409 with one row sourced from under `zips/`". It held 7,408, and
§1's `_source_file` breakdown shows why: one batch, six source files, all six the
expected lookup CSVs in the month root, no NULL `lookup_type`, nothing from
outside the set.

Tracing the prediction back, it conflated a transient state with a persisted one:

- The probe that took lookup **staging** 7,408 → 7,409 was a deliberate **Task 6
  deployment-spike** probe (`autoloader.py`'s docstring cites it as the evidence
  that cloudFiles lists recursively). It was a temporary experiment, not a
  lingering defect.
- The old lookup stream carried `pathGlobFilter="*CSV"` precisely to survive the
  shared root, so a `probe.txt` could not reach bronze through the normal flow.
- `docs/f1.3-estabelecimentos-run-evidence.md` records the check under "The lookup
  pipeline was not disturbed": `SELECT count(*) FROM bronze_cnpj_lookup` → 7,408,
  "unchanged from F1.2's evidence". It was already reconciled and stayed that way.

So the reload's value is not that it removed bad rows. It is structural: the
`pathGlobFilter` — a discovery *rule*, which fails silently when a source filename
drifts out of its pattern — is replaced by a per-table subdir, which cannot
under-ingest quietly. And bronze is now single-batch and append-only from its
first commit, so "did we duplicate?" never needs asking again.

Recorded as a deviation because the brief set the expectation explicitly, and
"expected smaller, got identical" needs an explanation rather than silence — even
though the explanation is benign.

### Not a deviation, but worth stating

- `scripts/migrate_lookups_to_subdir.py` prints `bundle deploy` as its step 1. In
  this execution the deploy happened **before** the migration, because the backfill
  needed it. That is strictly safer than the printed order — the old
  month-root-recursive wheel was never live while the new subdir existed — and it
  is why the second `clear_state` found nothing to remove.
- The migration script's printed step 0 was satisfied by §1, taken before the
  script ran rather than after. Same reference, earlier.

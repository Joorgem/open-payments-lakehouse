## Run 2 — stretch: prove the gate blocks a corrupted batch

**Setup.** Uploaded one deliberately malformed file to the *same* landed
month path (`.../landing/cnpj/2026-06/F.K99999$X.D99999.QUALSCSV`, cp1252
bytes) so Auto Loader's checkpoint would pick up only the new file on the
next run:

```
"XX";""
"01";"desc";"EXTRA"
```

Row 1 has an empty `descricao` (`""`); row 2 has a third field beyond the
2-column lookup schema.

**Result:** `result_state = FAILED`, `life_cycle_state = INTERNAL_ERROR`,
state message: *"Task fail_on_dq failed with message: Workload failed, see
run output for details. This caused all downstream tasks to get skipped."*

Per-task states:

| task_key | result_state | life_cycle_state | notes |
|---|---|---|---|
| `ingest` | SUCCESS | TERMINATED | picked up only the 1 new file (Auto Loader checkpoint) |
| `dq_gate` | SUCCESS | TERMINATED | stdout: `dq_gate: good=7409 bad=1` |
| `check_bad_rows` | SUCCESS | TERMINATED | condition `bad_row_count == 0` → outcome `"false"` |
| `promote` | EXCLUDED | SKIPPED | "Excluded because its conditional dependency on check_bad_rows was not met." — **promotion correctly blocked** |
| `fail_on_dq` | FAILED | TERMINATED | `SystemExit: 1` (ran twice — attempt 0 and a platform-retried attempt 1, both FAILED); this is the task that flips the whole run to `FAILED` |

DQ gate: **good=7409, bad=1** (net +2 rows ingested from the 1 new file;
1 promotable, 1 rejected).

**Reality vs. expectation (worth recording honestly):** of the two crafted
bad rows, only the *empty-`descricao`* row (`"XX";""`) was actually rejected,
via the `null_or_empty_descricao` rule (`_dq_reject_reason`) — `descricao`
landed as SQL `NULL`, not `""`. The *extra-field* row (`"01";"desc";"EXTRA"`)
was **not** captured into `_rescued_data` as expected — Spark's CSV reader
silently dropped the trailing third field and the row parsed as
`codigo="01", descricao="desc"`, which passed all DQ rules and was counted as
good. So `rescuedDataColumn` did not populate for a fixed-width schema with a
trailing extra CSV field in this configuration. This did not block the stretch
goal — the empty-`descricao` row alone was sufficient to drive
`bad_row_count=1` and flip the gate — but it's a real, documented limit of the
`_rescued_data` check as currently wired, not something to gloss over.

## Design note: fail-closed gate semantics

The DQ gate evaluates the ENTIRE staging table on every run, and rejected
rows are copied (not moved) to quarantine. A single bad row therefore
blocks promotion on all subsequent runs until staging is manually cleaned
— exactly what Run 2 → Run 3 demonstrated (manual `DELETE FROM ...staging`
before the recovery run). This is a deliberate fail-closed posture for the
F1.2 bronze slice; batch-scoped gating (filter by `_batch_id`) is the
planned evolution when multi-month ingestion lands.

Known seam for the next phase: the ingest entrypoint currently pins the
snapshot month from `opl.config` (`2026-06`), and `promote` overwrites the
bronze table from the whole staging content without a month discriminator
or dedup — ingesting a second month requires parameterizing the month and
adding a snapshot key. Tracked for F1.3+.

**Realistic recovery** (bad row inside a REAL lookup file): the Run 3
procedure (DELETE by `_source_file` + remove the file) only works for an
isolated poison file. For a bad row co-located with good rows in a real file,
deleting that file's staging rows would silently drop the whole lookup_type
— the Auto Loader checkpoint already marks the file consumed and will not
re-read it. Recover instead by re-landing a corrected copy under a NEW file
name (the checkpoint picks it up) and then deleting only the original file's
staging rows, or by resetting the checkpoint AND truncating staging together.

## Run 3 — recovery after cleanup

**Cleanup performed before this run** (required because `dq_gate` re-evaluates
the *whole* staging table on every run, not just the new batch):
1. `DELETE FROM workspace.default.bronze_cnpj_lookup_staging WHERE _source_file LIKE '%F.K99999%'` → 2 rows deleted.
2. `DELETE FROM workspace.default.bronze_cnpj_lookup_quarantine WHERE _source_file LIKE '%F.K99999%'` → 1 row deleted.
3. `databricks fs rm dbfs:/Volumes/workspace/default/landing/cnpj/2026-06/F.K99999$X.D99999.QUALSCSV --profile opl-free` — removed the injected file from the volume.

**Result:** `result_state = SUCCESS`, identical shape to Run 1.

| task_key | result_state | life_cycle_state | notes |
|---|---|---|---|
| `ingest` | SUCCESS | TERMINATED | no new files (checkpoint already past the 6 real files; the injected file was deleted, not re-processed) |
| `dq_gate` | SUCCESS | TERMINATED | stdout: `dq_gate: good=7408 bad=0` |
| `check_bad_rows` | SUCCESS | TERMINATED | outcome `"true"` |
| `promote` | SUCCESS | TERMINATED | stdout: `promote: wrote 7408 rows to workspace.default.bronze_cnpj_lookup with constraints` |
| `fail_on_dq` | EXCLUDED | SKIPPED | as expected |

DQ gate back to **good=7408, bad=0** — full recovery to the pre-stretch state,
confirmed identical to Run 1's counts.

databricks warehouses list --profile opl-free --output json

databricks api post /api/2.0/sql/statements --profile opl-free --json \
  '{"warehouse_id":"<WAREHOUSE_ID>","statement":"SELECT lookup_type, count(*) c FROM workspace.default.bronze_cnpj_lookup GROUP BY lookup_type ORDER BY lookup_type","wait_timeout":"30s"}'

# stretch: inject a corrupted file into the same landed month path

  '{"warehouse_id":"<WAREHOUSE_ID>","statement":"DELETE FROM workspace.default.bronze_cnpj_lookup_staging WHERE _source_file LIKE '"'"'%F.K99999%'"'"'","wait_timeout":"30s"}'
databricks api post /api/2.0/sql/statements --profile opl-free --json \
  '{"warehouse_id":"<WAREHOUSE_ID>","statement":"DELETE FROM workspace.default.bronze_cnpj_lookup_quarantine WHERE _source_file LIKE '"'"'%F.K99999%'"'"'","wait_timeout":"30s"}'
databricks fs rm "dbfs:/Volumes/workspace/default/landing/cnpj/2026-06/F.K99999\$X.D99999.QUALSCSV" --profile opl-free

# run 3 (recovery)

databricks jobs get-run <RUN_ID> --profile opl-free --output json

Notes on this environment: this shell is Git Bash on Windows, which
rewrites arguments that look like absolute Unix paths (e.g. `/api/2.0/...`)
into Windows paths before exec — `databricks api get|post` calls needed
`MSYS_NO_PATHCONV=1` set to stop that rewrite from mangling the REST path.

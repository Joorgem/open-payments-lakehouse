# F1.4b PR A — Empresas and Socios, Real Run Evidence

The live `2026-06` ingest of `empresas` and `socios` against the Free Edition
workspace on **2026-08-01**, from branch `feat/f1-4b-empresas-socios` at
`ba59bbb`. PR A only: `2026-07` and the `delta.dataSkippingStatsColumns`
measurement belong to PR B.

Host names, org/workspace IDs and full `run_page_url`s are redacted, as in the
F1.2, F1.3 and F1.4a evidence docs. Job ids, batch ids, counts and byte counts
are verbatim.

**No personal name appears in this document.** `socios` is the one table in this
lakehouse that names natural persons, and [ADR 0008](adr/0008-pii-masking-socios.md)
is the control over it. The triage of its 1,797 rejected rows in [§4](#4-socios--the-gate-fired-again-1797-times)
is done entirely by counts and by non-name columns. That was a constraint on the
evidence and it cost nothing: every question the triage had to answer was
answerable without reading a name.

**Four things this run settled that were previously only argued.** Multipart
upload had never run against this workspace and its geometry was computed rather
than observed ([§2](#2-the-upload--and-the-nine-objects-that-were-not-multipart));
the two new rule sets and the two new rules had never been evaluated against real
data ([§8](#8-the-new-rules-first-run)); the mask had never been applied to a real
socios table, let alone verified by reading through it ([§7](#7-the-mask-verified-by-behaviour--not-by-ddl));
and the DQ gate had never been exercised on a table this phase added
([§3](#3-empresas--the-gate-fired), [§4](#4-socios--the-gate-fired-again-1797-times)).
Two of the four came out differently from what the design documents predicted,
and those are the useful ones: ADR 0007 was wrong about which upload path this
phase's objects take, and both jobs ended on `fail_on_dq` rather than on
`promote`.

**And one thing this phase claimed that a `git diff --stat` appears to refute.**
The plan's premise was that a new table costs no file under `databricks/src`; the
branch modifies three files there. The claim survives, with an asterisk it should
have carried from the start, and [§9](#9-the-three-files-under-databrickssrc-and-which-of-them-a-table-cost)
is the per-commit accounting — one command, run it before believing either side.

## 1. Pre-state, and the stale wheel that would have failed the run

Taken before anything was uploaded or deployed.

`workspace.default` held only the six estabelecimentos and lookup tables. There
was no `bronze_cnpj_socios` and no empresas table of any kind — **a clean slate,
which is what makes ADR 0008's "the control was applied when the data landed"
achievable rather than merely intended.** Had a socios bronze table already
existed, the mask would necessarily have followed the data. It did not exist, so
the ordering in [§7](#7-the-mask-verified-by-behaviour--not-by-ddl) is a fact about
this run and not an argument about it.

No `_probe_*` tables were left behind by the mask/CHECK probe that ADR 0008
records; that probe cleaned up after itself.

One pre-flight check failed, and it would have failed the run:

```
dist/*.whl  dated 2026-07-31 11:25
```

That wheel predates **every commit on this branch**. It carried socios *with* the
`CHECK` constraint Unity Catalog refuses on a masked table, and carried no
`opl.bronze.masking` at all — so `ensure_masked_table.py`, the first task of the
socios job, would have died on import, and had it somehow not, `promote_batch`
would have appended the rows and then failed re-asserting a `CHECK` that cannot
exist. That is precisely the unrepairable failure ADR 0008 describes, and the
stale artifact was the way back into it.

Rebuilt: **53,385 → 79,145 B**. The rebuilt wheel was verified to carry
`opl.bronze.masking`, to declare socios with its two `SET NOT NULL` statements
and no `CHECK`, and to carry the import-time mask/CHECK guard.
`bundle deploy -t free` then rebuilt it again from `HEAD`, so what ran on the
workspace was built from the deployed commit and not from a local artifact.

Worth stating plainly: a stale build artifact is invisible to every test in this
repository. CI ran green on `ba59bbb`; the wheel on disk was from the previous
day. Nothing but the timestamp check caught it.

## 2. The upload — and the nine objects that were **not** multipart

Twenty zips, from local disk into
`/Volumes/workspace/default/landing/cnpj/2026-06/zips/{empresas,socios}/`.

```
13:32:13 -> 14:03:15   =  31 m 02 s   20/20 objects, both exits 0
```

| group | objects | bytes |
|---|---|---|
| Empresas | 10 | 1,352,336,436 |
| Socios | 10 | 680,600,148 |
| **total** | **20** | **2,032,936,584** |

Both group totals match the local disk measurement **byte for byte**, and the
post-PUT `content_length` check inherited from F1.3's incident 1 passed on every
object.

### What the run contradicted

[ADR 0007](adr/0007-multipart-upload.md) states, as a durable property of this
repository's uploads, that "our objects are the Estabelecimentos zips at
320 MB–2.13 GB, above every threshold any version has used, so on any SDK from
0.45.0 onward every upload this repo performs is multipart". **That is false for
this phase's tables.**

| objects | size | against the 52,428,800 B floor | path taken |
|---|---|---|---|
| `Socios1.zip` … `Socios9.zip` | 49,125,139 – 49,737,629 B | **below** | single PUT |
| the other eleven — `Empresas0`–`9`, `Socios0` | — | above | multipart |

**Nine of the twenty went single PUT.** The ADR generalised from the one table
group that existed when it was written: Estabelecimentos' parts run 320 MB–2.13 GB
and clear every threshold any SDK version has used, and the RFB's Socios parts do
not.

This was an accident, and it bought the better measurement.

### The measurement the accident bought

Both paths ran over the same link, in the same run, minutes apart, on nine
objects each:

| subset | objects | bytes | wall clock | throughput |
|---|---|---|---|---|
| Empresas1–9 — **multipart** | 9 | 816,029,823 | 517 s | **94.7 MB/min** |
| Socios1–9 — **single PUT** | 9 | 444,421,834 | 1,076 s | **24.8 MB/min** |
| whole run | 20 | 2,032,936,584 | 31 m 02 s | **65.5 MB/min** |

**Multipart moved bytes 3.8× faster than single PUT.** ADR 0007 adopted multipart
on the strength of its retry semantics — the unit of retry becomes a part rather
than the whole file — and explicitly did not claim a throughput benefit. It has
one, and this is the first time anyone here could say so from observation. It is
a controlled comparison in the way that matters (same link, same session, same
client, adjacent in time) and uncontrolled in the way that limits it (different
files, different remote paths, one sample of each).

`Empresas0.zip` and `Socios0.zip` are in neither subset; only these two
nine-object stretches were timed separately.

**65.5 MB/min against the ~67 MB/min ADR 0007 assumed.** That rate is the input
to the ADR's re-derivation of `UPLOAD_RETRY_TIMEOUT_SECONDS` from 2 h to 30 min,
and it was carried over from F1.3's measurement of a different link on a different
day. It survives contact with this run, so the 30-minute per-part budget is
**consistent with the throughput actually observed** — the assumption it was
derived from is no longer only an assumption. Note that the whole run's rate is
dragged down by the nine single-PUT objects; the multipart path alone ran well
above it.

### What the upload does *not* settle

**The timeout itself was not exercised, and "consistent with" is the strongest
thing this table supports.** These twenty rows are whole-object transfers and an
aggregate rate. The 30-minute budget is a per-*part* budget, and neither of the
two things it exists for was observed: no single 50 MiB part was timed, and
nothing stalled long enough for the timeout to release a part. This paragraph said
"correctly sized, now by observation" until CodeRabbit read it on PR #6; that
sentence claimed evidence for a per-part property from a whole-run measurement.

Per-part retry recovery is likewise still argued from the SDK's code and not from
an observed recovery. Nothing failed during these 31 minutes, so nothing retried.

### The triage

One row, of the 68,629,148 staged:

| column | value |
|---|---|
| `cnpj_basico` | `08314885` |
| `razao_social` | NULL |
| `natureza_juridica` | `0000` |
| `qualificacao` | `00` |
| `capital_social` | `0,00` |
| `porte` | NULL |
| `_rescued_data` | **NULL** |

`_rescued_data` NULL is the load-bearing one. It means Auto Loader parsed the
expected number of fields — so this is **not** a misparse of the kind F1.3's
incidents 3 and 4 produced, where a well-formed-looking row hid a reader defect.
The record arrived from the RFB with the shape the contract expects and with no
name in it. `natureza_juridica` `0000` is the RFB's own *not informed* code and
`capital_social` is `0,00`: a genuine shell record in the public register.

The completeness rule that caught it is the one redesigned in Task 2 — the F1.4
spec's version would have rejected nearly every row in the table. On its first
run against real data it found **exactly one** real anomaly in 68,629,148 rows,
and the anomaly is in the source rather than in us.

### The repromote

Repromoted by explicit human decision, through `repromote_triaged_batch`, which
re-applies the same rules and appends only passing rows:

```
promote_batch: appended 68629147 rows (batch 321750543973966)
```

The one rejected row **stays in quarantine**. Bronze count verified independently
through the SQL warehouse, not read from the task's own log:
**68,629,147 = 68,629,148 − 1. Exact.**

## 5. Row reconciliation — the control, not the paperwork

| table | staged | rejected | bronze | source files |
|---|---|---|---|---|
| `bronze_cnpj_empresas` | 68,629,148 | 1 | **68,629,147** | 10 |
| `bronze_cnpj_socios` | 27,838,448 | 1,797 | **27,836,651** | 10 |

Both exact. Ten source files each, matching the ten zips uploaded per table in
[§2](#2-the-upload--and-the-nine-objects-that-were-not-multipart).

This table is here because of F1.3. Its incident 3 — a reader that split records
on newlines inside quoted fields — was invisible to the *total* row count, because
the split added a row and quarantining the fragment removed one, so bronze held
exactly the right number with a damaged record inside it. What exposed it was the
**regularity of the per-part counts**: the RFB ships fixed-size parts, so parts
1–9 of Estabelecimentos hold 4,753,435 rows each, to the row, and a deviation is
visible without any reference outside the data.

So a reconciliation that only checks `staged − rejected = bronze` is weaker than
it looks. What makes the numbers above a control rather than an arithmetic
identity is that they came from three independent places — the ingest's staging
count, the gate's reject count, and a `count(*)` over bronze through the SQL
warehouse — and that the file count is 10 on both tables, matching the objects
uploaded.

**Per-part row counts were not captured for these two tables.** That is a gap
against what F1.3 learned, and it is stated here rather than left to be noticed:
a per-`_source_file` breakdown is what would let a future reader see the RFB's
split regularity in empresas and socios the way F1.3's evidence doc shows it for
estabelecimentos. The whole-table reconciliation above is exact; the finer control
was not exercised.

## 6. The reject rate, measured — and deliberately not acted on

| table | rejects | of | rate |
|---|---|---|---|
| `empresas`, 2026-06 | 1 | 68,629,148 staged | 1 in 68,629,148 |
| `socios`, 2026-06 | 1,797 | 27,838,448 staged | **0.0065 %** |

For comparison, the only other rate this project has measured is ADR 0006's
estabelecimentos baseline: 4 in 42.8M, about 1 in 10.7 million.

**Nothing about the gate changed because of these numbers, and that is the
decision, not an omission.** ADR 0006 Decision 3 specifies rate-based gating —
block promotion when the reject rate exceeds a threshold, otherwise quarantine and
continue — and defers it to no phase, on the explicit ground that "the threshold
must be chosen against measured history, not guessed". F1.4a corrected that
deferral once already, because it had named a phase that then did not take it.

Recording the rate here **is** this phase's whole obligation on it. Two more
observed cells now exist, and the spread between them and the estabelecimentos
baseline is itself the useful finding: socios rejects at 0.0065 %,
estabelecimentos at about 1 in 10.7 million, and empresas at 1 in 68,629,148.
A single threshold across all four tables would either be useless on socios or
would let a real encoding shift through on estabelecimentos, which is the failure
mode Decision 3 exists to catch. Whoever eventually sets one will need it per
table, and will need more than one month per table. This phase supplies two cells
of that history and changes no behaviour.

### No reject reason was retired

Task 2 generated the required-field reasons one per column from `REQUIRED_FIELDS`,
and the diff is **purely additive**: `null_or_empty_codigo`,
`null_or_empty_cnpj_ordem` and `null_or_empty_cnpj_dv` come out byte-identical to
the strings F1.2 and F1.3 shipped, and estabelecimentos keeps all five of its
existing reason strings and gains `null_or_empty_municipio`. So **no historical
quarantine row carries a reason name the code no longer produces**, and no
translation table is needed to read the older quarantines. This is recorded
because the plan asked for the retired names, and the answer is that there are
none.

## 7. The mask, verified by behaviour — not by DDL

### The ordering, which is the actual deliverable

While the socios batch sat gated — after `ensure_masked_table`, after the ingest,
before the repromote — **`workspace.default.bronze_cnpj_socios` existed with 0
rows.**

That is the sentence ADR 0008 was written to be able to make. The table was
created and both masks were attached *before any personal name was written to it*.
Every other bronze table in this repository is created implicitly by
`promote_batch`'s append, which would have meant creating socios with the names
already in it and masking afterwards. "The control was applied when the data
landed" and "I went back and masked it afterwards" are different sentences, and
this run is what makes the first one true rather than intended.

### Attachment

```sql
SELECT * FROM system.information_schema.column_masks;
```

| column | mask |
|---|---|
| `nome_socio_razao_social` | `workspace.default.mask_personal_name` |
| `nome_do_representante` | `workspace.default.mask_personal_name` |

**Both** columns. The F1.4 spec named only `nome_socio_razao_social`; ADR 0008
widened it to both on the argument that `nome_do_representante` is a civil name
on every row that has one. That widening is now applied in the live catalog and
not only in a design document.

### Behaviour

Attachment is not the control; what a reader sees is. So the table was read.

```sql
SELECT nome_socio_razao_social, count(*)
FROM workspace.default.bronze_cnpj_socios
GROUP BY nome_socio_razao_social;
```

**Exactly one row came back: `***`, count 27,836,651.** Over the whole table, not
a `LIMIT 5`. One distinct value across every row in bronze, and the count equals
the promoted count from [§5](#5-row-reconciliation--the-control-not-the-paperwork)
exactly. There is no unmasked row.

A control query on the same rows, to establish that the query itself is not simply
broken — unmasked columns return real data:

| column | value |
|---|---|
| `cnpj_basico` | `08197503` |
| `qualificacao_socio` | `49` |

**Fail-closed, confirmed in practice.** `opl_pii_readers` does not exist in this
workspace, `is_account_group_member` therefore returns false, and the value
returned is the masked one — to the table owner's own query. The control degrades
toward hiding. That is the direction ADR 0008 chose and this is it working.

### The limit, restated because this run did not remove it

`bronze_cnpj_socios_staging` and `bronze_cnpj_socios_quarantine` hold the partner
names **in the clear**. Neither passes through `ensure_masked_table`; both are
created by their own writers. Nothing in this run changed that, and the run put
sizes on it:

- **`bronze_cnpj_socios_staging` took all 27,838,448 ingested rows**, names in the
  clear. It is the frame the gate evaluates and the promote reads. Every name that
  reached masked bronze passed through it unmasked first.
- **`bronze_cnpj_socios_quarantine` holds the 1,797 rejected rows** — and this is
  the table a human is *expected* to open, which the triage in
  [§4](#4-socios--the-gate-fired-again-1797-times) is exactly an instance of. Those
  1,797 have a null `nome_socio_razao_social`, since that is why they were
  rejected; what they hold in the clear is the rest of a personal record. Their
  `nome_do_representante` was not examined in either direction, so nothing is
  claimed about it here.

The triage above was deliberately performed without selecting either name column,
which is a discipline and not a control.

**That paragraph closed with a claim the PR #6 review disproved, and the correction
belongs here rather than only in the ADR.** It said the `CHECK`/mask incompatibility
"applies to staging and quarantine too, so extending `ensure_masked_table` to all
three is the same decision again". It does not. `promote_batch._assert_constraints`
issues constraint DDL against the **bronze** table only, and neither the staging nor
the quarantine table has ever carried a constraint — nothing stopped a mask on
either. What actually separates them is different and larger: masking **quarantine**
costs nothing and has since been implemented, while masking **staging** would make
the next promote read `***` and write it into bronze, and would make the DQ gate
evaluate the missing-name rule against a value that is neither null nor empty. See
[ADR 0008 → The boundary](adr/0008-pii-masking-socios.md#the-boundary-quarantine-is-masked-too-staging-cannot-be).

What this run observed stands as written: on 2026-08-01, both tables held the names
in the clear.

## 8. The new rules' first run

### `unprovable_snapshot_ref_date` fired and found nothing

The rule refuses a row whose `_snapshot_ref_date` is NULL — the value Delta fills
in when the metadata step silently stops producing the column. It ran against both
tables and found **0 rows** on each, which is the correct outcome and the only one
that would have let the batches through.

### No "skipped rules" line appeared in either run log

This is the other half, and it is worth as much as the rule firing. Task 3 added
`skip_notice`, which prints a line when a rule's declared column is absent from the
frame, because a gate that quietly stops applying a rule and then reports the batch
clean is indistinguishable, in the log, from a gate that applied it and found
nothing. The notice returns `None` — no line at all — on a healthy path, on the
argument that a warning printed on every run is one an operator learns to scroll
past.

Both empresas and socios staging are created fresh at 37 columns and carry every
column their rules declare, so **neither run printed the line**. Task 3's notice
correctly stayed silent. The silence is evidence only because the mechanism that
would have broken it is understood: see the carry-forward in
[§10](#10-what-this-does-not-establish-and-what-it-hands-forward) for the one live
table where that mechanism is currently latent.

### The pre-run measurements that made the new rules safe to add

Task 2 widened the U+FFFD encoding check from 2 columns to all 30, and added
`municipio` to estabelecimentos' required fields. Both changes apply to a **live
71.9M-row table**, and a required-field rule that rejects existing rows would
strand the next estabelecimentos batch. So they were measured before they were
written, over `workspace.default.bronze_cnpj_estabelecimentos` (71,874,448 rows):

| measurement | result |
|---|---|
| blank `municipio`, `situacao_cadastral`, `uf`, `data_inicio_atividade` | **0** |
| rows containing U+FFFD (`chr(65533)`), each of all **30** columns | **0** |

Neither the new required column nor the widened encoding check rejects any row
that exists in that table today.

The 30-column scan also touches F1.3's open question — the one record in part 8
carrying a byte `cp1252` cannot decode, which Java is expected to replace with
U+FFFD silently — and it does not close it. **Zero hits across all 30 columns of
71,874,448 rows** is in tension with expecting exactly one substituted character
somewhere in that table. This measurement does not resolve where the tension lies:
it was taken to de-risk widening the encoding rule, not to hunt for that record,
and it says nothing about whether the record survived F1.3's rebuild, which column
would hold the byte, or whether the substitution happened at all. Recorded because
it is a measurement someone will otherwise redo, and because an unexplained zero
is worth more written down than assumed away.

## 9. The three files under `databricks/src`, and which of them a table cost

The plan for this phase opens by naming what it is testing: "Two new `BronzeTable`
literals, two rule sets, two job YAMLs — and **no file under `databricks/src`**.
That is the F1.4a thesis being tested, not restated."

A reader who runs `git diff --stat` against this branch finds three files under
`databricks/src`, and is entitled to conclude the claim was oversold. **The claim
does need an asterisk, and here it is in the claim's own words:** adding a table
cost two registry literals, two rule sets and two job YAMLs, and modified no file
under `databricks/src`. *Masking* a table cost one new file there. And two files
that were already there changed once each, for a reason that has nothing to do
with either new table. The plan said "no file"; it should have said "no existing
file, plus the one the mask needs" — and its own file-by-file table, lower in the
same document, already listed `databricks/src/ensure_masked_table.py` as
**Create**. The architecture line was overstated against the rest of the document
it opens, on the day it was written.

The whole accounting is one command. Of every commit between `main @ b3cbbba` and
this branch's tip, exactly three touch `databricks/src`:

```
$ git log --oneline --name-only b3cbbba..HEAD -- databricks/src
f02ff97 fix(registry): drop socios' CHECK constraint and make the mask/CHECK pair unreachable
databricks/src/ensure_masked_table.py
b48d87e feat(governance): mask both personal-name columns before socios data lands
databricks/src/ensure_masked_table.py
ae61b92 fix(dq): say out loud which DQ rules did not run against a batch
databricks/src/dq_gate_batch.py
databricks/src/promote_batch.py
```

### The commits that added the tables touch nothing there

| what a table cost | commit | files | under `databricks/src` |
|---|---|---|---|
| both registry entries | `8ece124` | `src/opl/bronze/registry.py`, `tests/bronze/test_registry.py` | **0** |
| both rule sets | `caed88e` | `src/opl/bronze/rules.py` + 2 test files | **0** |
| both job YAMLs | `ba59bbb` | the 2 YAMLs, `pyproject.toml`, `tests/test_task_wiring.py`, `uv.lock` | **0** |

```
$ git show --stat 8ece124      # 2 files, 243 insertions(+), 12 deletions(-)
$ git show --stat caed88e      # 3 files, 559 insertions(+), 37 deletions(-)
$ git show --stat ba59bbb      # 5 files, 668 insertions(+),  1 deletion(-)
```

One honest qualification on `caed88e`: it is not purely per-table. It added the
`"empresas"` and `"socios"` entries to `REQUIRED_FIELDS` and to the rule-set map,
and in the same commit widened the U+FFFD check from 2 columns to all 30 and added
`municipio` to estabelecimentos' required fields — the cross-cutting half measured
in [§8](#8-the-new-rules-first-run). The per-table half of that diff is the two new
`REQUIRED_FIELDS` entries and the two new rule-set blocks; the rest is the
mechanism they hang off, and it is shared by all four tables.

### `ae61b92` is a DQ change, not a per-table cost

It modified `dq_gate_batch.py` (+58/−28) and `promote_batch.py` (+32/−2), and
**neither hunk names `empresas` or `socios`** — no added line under
`databricks/src` in that commit mentions either table:

```
$ git show --stat ae61b92 -- databricks/src
$ git show ae61b92 -- databricks/src | grep -iE '^\+.*(empresas|socios)'   # no output
```

What it changed is the subject of [§8](#8-the-new-rules-first-run): a rule whose
declared column is absent from the frame is correctly skipped and was silently
skipped, so `dq.skip_notice` now returns a run-log line naming the rule, the
column, the table, the consequence and the remedy. It returns `None` on a healthy
path. The two job tasks are where it is emitted, and that is why they are the files
that changed: `dq.evaluate` runs on bare contract frames in unit tests constantly
and must not go noisy, so the emitter has to be the task layer.

The path that made it necessary is estabelecimentos' — rebuild plus repromote
against the 35-column `bronze_cnpj_estab_staging`, the table this phase never
touched. **This diff would have been identical had F1.4b added no table at all.**
It is in this branch because building two tables is what surfaced it, which is a
statement about when it was found and not about what it cost.

### `ensure_masked_table.py` is genuinely new, and the reason is ordering

77 lines, created in `b48d87e` and corrected in `f02ff97`. It is the ninth file
under `databricks/src` and the only one this branch added.

It exists because every other bronze table in this repository is created
*implicitly*, by `promote_batch`'s first append. For socios that would mean
creating the table with the personal names already inside it and attaching the mask
afterwards — and "the control was applied when the data landed" would have been
false. There is no way to reorder that from a registry entry, a rule set or a YAML:
something has to issue `CREATE TABLE` and `ALTER COLUMN ... SET MASK` before the
first byte arrives, and on Databricks that something is a job task.
[§7](#7-the-mask-verified-by-behaviour--not-by-ddl) is the receipt:
`bronze_cnpj_socios` existed with **0 rows** while the batch sat gated.

So the file is the cost of *masking* a table, paid once, and it is a no-op for any
contract that declares no masked column. The next masked table adds a registry
entry, a rule set, a job YAML and one line in `MASKED_COLUMNS` — and no file here.
`test_only_the_masked_table_creates_its_bronze_table_up_front_and_does_it_first`
(`tests/test_job_yaml_wiring.py`) asserts both directions of that, so a job
carrying the task for an unmasked table fails CI.

### What the seam actually held

Six of the nine files under `databricks/src` are untouched by this branch, and the
two that changed did so for a reason no table caused. Stated as the narrow,
checkable claim: **adding `empresas` and `socios` modified zero existing files
under `databricks/src`**, and the one-line proof is the `git log` at the top of
this section.

## 10. What this does not establish, and what it hands forward

- **Staging and quarantine held the names in the clear during this run**
  ([§7](#7-the-mask-verified-by-behaviour--not-by-ddl)), and quarantine is the table
  a human opens — 1,797 rows of personal data went into it, and all 27,838,448 rows
  passed through unmasked staging on their way to masked bronze. The PR #6 review
  closed half of that: `ensure_masked_table` now masks the **quarantine** table as
  well, which reaches the workspace on its next authorised run. Staging stays
  unmasked on purpose, because a mask there would put `***` into bronze — see
  [ADR 0008 → The boundary](adr/0008-pii-masking-socios.md#the-boundary-quarantine-is-masked-too-staging-cannot-be).
  Neither change is retroactive: the rows landed unmasked once, and that is a fact
  about 2026-08-01 that no later DDL edits.
- **The 1,797 nameless socios are a modelling problem, not just a data-quality
  one.** If the vault models `socio` as an entity, they are hubs with no business
  identifier: they carry a CPF and a qualification code, and no name. Leaving them
  quarantined is right for bronze, whose job is to record what the source
  asserted. Silver and the vault will meet the same 1,797 rows and will have to
  decide something different about them.
- **Per-part row counts were not captured** for either new table
  ([§5](#5-row-reconciliation--the-control-not-the-paperwork)). The F1.3 control
  that caught a silent parse defect is therefore not exercised here.
- **The multipart throughput comparison is one sample of each path**
  ([§2](#2-the-upload--and-the-nine-objects-that-were-not-multipart)), over
  different files. Per-part retry recovery remains unobserved.
- **The mask is verified in a workspace where `opl_pii_readers` does not exist.**
  Every reader sees `***`, including the owner. Nothing here demonstrates that a
  member of that group sees the name, because there is no group and no member.
  Creating it, and the grants around it, is F4.
- **One month, two tables.** Every snapshot column still holds exactly one value,
  so nothing here shows the snapshot key discriminating. PR B lands `2026-07` and
  that is the run that tests it.
- **`unprovable_snapshot_ref_date` is currently inert for estabelecimentos.**
  `bronze_cnpj_estab_staging` is still the 35-column pre-F1.4a shape and carries
  neither snapshot column, so a repromote from it would skip the rule — audibly
  now, thanks to `skip_notice`, but skip it. It is not inert for the two tables in
  this PR, whose staging tables were created fresh at 37 columns.
- **Two prerequisites stand between PR B and its first ingest**, both found by
  measurement during this phase and neither recorded in the F1.4 spec, the plan or
  the F1.4a handoff:
  1. `bronze_ingest.py` writes staging with no `mergeSchema`, so the next
     estabelecimentos ingest sends a 37-column stream into the 35-column
     `bronze_cnpj_estab_staging` and **fails loudly at the Delta write**. Loud, not
     silent — but it stops the run. An unplanned migration step.
  2. `src/opl/bronze/registry.py` is at 796 of the 800-line limit, and PR B adds
     tables to that exact file. It must be split first, as
     `tests/bronze/test_registry.py` already was.
